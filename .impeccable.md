# IncubaCloud — Design Context

This file guides all design work on the IncubaCloud SPA (`/cloud/ui`, OWL, bundle
`incubacloud.assets_prod`) and any future surfaces (public site, SaaS tenant UI,
tenant admin dashboard). It is the source of truth when the `impeccable` skills run.

## Design Context

### Users

**Primary audience: Odoo partner technicians** — consultants, developers and sysadmins
working at a desk, usually alongside a terminal. They deploy and maintain doodba-based
Odoo instances on their own VPS servers. They are comfortable with SSH, Docker, copier
and duplicity, but their *experience levels vary a lot* — from senior devs to partners
who are adopting the module for the first time.

**Secondary audience (future): SaaS tenants** — less technical admins/owners of a
hosted Odoo. They will touch a subset of the same screens. The design must not assume
operator-level comfort everywhere.

**Context of use**: desktop-first, long sessions, frequently during incidents
(failed deploy, broken instance, restore from backup). The app lives next to logs and
a terminal, so it should feel *consistent* with that environment, not fight it.

**Jobs to be done**: register a host → create a project → deploy an instance →
monitor live SSH jobs → rebuild safely → list/restore backups → clone to staging →
triage alerts. Everything is observable and recoverable; nothing is magic.

### Brand Personality

**Three words**: **warm · approachable · partner-friendly.**

Technical, but not tribal. The UI should feel like a well-run workshop where every
tool is labelled — not a flight deck, not a hacker set, not a consumer SaaS. Partners
should feel *welcomed into* the tool, not intimidated by it.

**Emotional goal**: the user feels **in control**. Everything is visible — jobs,
logs, system state, failures. Transparency is the brand. When something is on fire,
the UI stays calm; when everything is fine, the UI stays quiet.

**Voice**: plain, helpful, human. Say what happened and what the user can do. No
marketing copy, no celebration language, no emoji, no "Oops!" No cutesy microcopy,
but also no terse sysadmin-speak that excludes newer partners.

### Aesthetic Direction

**Theme**: **dark-only**, refined. The current dark direction is correct — ops people
use it next to terminals and during long sessions — but the execution is generic. The
job is to *fix the generic bits*, not switch polarity.

**Warm, not cool**. Today's palette leans cool slate-blue (`#0F172A`, `#2563EB`).
Shift to *warm charcoal* surfaces — low-chroma neutrals tinted toward the brand's
amber/orange hue in OKLCH. The product should feel like a workshop at dusk, not a
data-center SOC at 3am.

**Typography**: distinctive but utilitarian. Move off **Inter** (banned by the skill,
and the defining font of the "AI developer tool" look we want to avoid). Move off
**JetBrains Mono** for the same reason. Pair a **warm humanist sans** for UI with a
**mono that has character** (reserved for logs, code, and numeric data — not
decorative chrome). Good candidate families to explore when the moment comes:
Switzer, General Sans, Satoshi, Bricolage Grotesque, Funnel Sans, Mona Sans (sans);
Commit Mono, Monaspace, Departure Mono, iA Writer Mono (mono). **Do not** reach for
anything in the skill's `reflex_fonts_to_reject` list.

**Color**: use **OKLCH** everywhere (not hex, not HSL). Tint the neutrals toward the
brand hue (~40–60° hue, chroma 0.005–0.015). Accent stays warm — refine the existing
orange (`#F97316`) into an OKLCH-balanced amber that reads well on warm charcoal.
**Retire the primary blue** (`#2563EB`) as a brand surface — keep it only as a
functional info color, desaturated. **60-30-10**: warm charcoal surfaces (60), soft
text and borders (30), the one amber accent (10).

### Anti-references — things this product must NOT look like

All four archetypes were explicitly ruled out. Match-and-refuse any of these patterns:

1. **Generic AI SaaS (Vercel / Linear clones)** — Inter, purple-blue gradients,
   glowing cards on dark, gradient text, identical card grids, hero-metric layouts,
   sparklines as decoration, `border-left: 3px solid var(--color-primary)` everywhere.
   This is the single biggest risk given the current stack.
2. **Classic Odoo backend** — Odoo purple, form-view density, heavy chrome, default
   Odoo icons. Nothing about IncubaCloud should feel like a stock Odoo module.
3. **Hacker / terminal cosplay** — all-monospace UI, green-on-black, scanlines,
   "matrix" effects, ASCII borders as decoration. There *is* a real terminal view in
   the product — that's the only place monospace is allowed to dominate.
4. **Consumer SaaS (Notion / Stripe)** — pastel illustrations, rounded mascots,
   playful empty states, confetti, "You did it!" celebration moments.

### Design Principles

These five principles override aesthetic instincts. When in doubt, re-read them.

1. **Warm operator calm.** Dark, but warm. Tinted neutrals, considered amber accent,
   zero cyan / purple / cool-slate chill. Feels like a well-lit workshop, not a SOC.

2. **Everything visible, nothing showy.** Jobs, logs, system messages, state changes
   are always accessible and legible. Decorative flourishes that don't help the
   operator understand what's happening get cut. No glass, no gradients, no glow.

3. **Quietly opinionated typography.** Distinctive font pairing, clear modular scale,
   hierarchy via size + weight (never via gradient or color). Monospace earns its
   place — it's for logs, code, and numeric data, never for "tech vibes."

4. **Approachable without being cute.** Microcopy is plain, helpful, human. Empty
   states *teach the interface*. Errors explain what happened and how to recover. But
   no mascots, no emoji, no playful illustrations — partners demo this to clients.

5. **One palette, used with restraint.** 60-30-10 discipline. One considered accent.
   No rainbow tag systems, no gradient CTAs, no "every state gets its own hue" chaos.
   Contrast and spacing do the heavy lifting.

### Hard rules (from the skill, reinforced here)

- **No `border-left:` / `border-right:` > 1px as coloured accent stripes** on cards,
  list items, callouts or alerts. Ever. Use a full border, a background tint, a leading
  icon, or nothing — rewrite the element, don't swap the stripe for `box-shadow inset`.
- **No gradient text.** No `background-clip: text` on gradients. Solid colours only.
- **No pure black (`#000`) or pure white (`#fff`).** Always tinted via OKLCH.
- **No Inter.** No DM Sans, Plus Jakarta, Outfit, Space Grotesk, Instrument Sans/Serif,
  IBM Plex family, Fraunces, Newsreader, Lora, Crimson, Playfair, Cormorant, Syne,
  Space Mono, DM Serif. Any font in the skill's `reflex_fonts_to_reject` list is out.
- **No JetBrains Mono** (same reason — the "developer tool" default).
- **No dark-mode-with-glowing-accents** as a shortcut for "looks cool." The dark theme
  has to be *designed*, not defaulted to.
