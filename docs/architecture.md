# Architecture

IncubaCloud Core is an Odoo module that acts as a **control plane** for remote Odoo infrastructure. It does not run workloads — it orchestrates them on external servers via SSH.

## Job execution pattern

All remote operations are modelled as `cloud.job` records and executed asynchronously by an OCA `queue_job` worker.

### Lifecycle

```
1. API call (e.g. deploy_instance)
   → cloud.job.enqueue(host_id, instance_id, 'deploy_instance', payload)
   → Server-side role gate per job type (manager-only types enforced here)
   → The type's queue rules: collapse, exclusive, the cap of five
   → Creates the cloud.job: a free target hands it to queue_job at once
     (a queue.job is created), a busy one keeps it `queued` until the
     dispatcher starts it (see "The job queue" below)

2. queue_job worker picks up queue.job
   → Calls cloud.job.execute()
   → Looks up the executor class in the registry
   → Asks executor.blocking_alert(): an alert returned ends the job at
     once, blocked on it (blocked_alert_id; resolving the alert
     dispatches it again) — the deploy's addon pre-flight. A step of a
     chain cannot wait: it fails instead, and the chain is cancelled
   → A job that starts again still cancelled — a person stopped it and
     its worker died before it stopped, so queue_job put it back in the
     queue — does not run: on_cancelled_running() closes it, with no
     step results (see "A worker that dies" below)
   → A failure before run() (a refused check) calls on_abort()
   → Calls executor.run()

3. AbstractSSHExecutor.run()
   → Opens asyncio event loop, connects via asyncssh
   → Runs commands from get_commands()
   → Streams stdout/stderr into a buffer, periodically flushed to
     cloud.job.log.chunk (fresh cursor)
   → Notifies the frontend via the PostgreSQL bus (cloud_jobs channel)
   → Calls on_success() or on_failure() in a fresh DB cursor; a run
     that ends with neither (a refused check, no connection, a hook
     that raised) calls on_abort() there instead, unless the job will
     be retried
   → A run a person cancels (the flag, polled between ticks) calls
     on_cancelled_running(): on_failure() with what the steps answered,
     or on_abort() before them, without raising alerts
     (ic_job_cancelled); the job still ends cancelled (issue #2). The
     flag is not read once the run has ended, nor once its outcome hook
     has started: what ended or began to close keeps its own outcome.
     So a hook that hangs is not cut off by a stop: the timeout of its
     SSH commands bounds it (DEFAULT_SSH_COMMAND_TIMEOUT, 1 h), and the
     panel may show the job cancelled while it still runs

4. Frontend (OWL)
   → Listens on bus channels cloud_jobs / cloud_overview
   → On job events: fetches /cloud/get_job_brief and toasts the outcome
   → Log terminal page: WebSocket stream with HTTP polling fallback
```

### Reliability guarantees

- **Serialization** — an instance runs one visible job at a time, and a host one host-level job at a time; what is asked for meanwhile waits in the target's queue. See [The job queue](#the-job-queue). Monitoring job types (`host_metrics`, `docker_prune`, `instance_health`, `read_last_login`, `capture_secret_key`; `pitr_status` and `pitr_base_backup` with `incubacloud_pitr`) are *hidden*: they never wait, never occupy a target, and stay out of the UI.
- **Transient connection retry** — executors that opt in (the monitoring probes) retry SSH connection failures up to 10 attempts (30 s backoff via `RetryableJobError`, ~10 min in all — sized to outlast a host's own maintenance reboot). Whether an attempt was the last is queue_job's decision, not the executor's: the critical `host_unreachable` alert is raised from the job's **terminal** `failed` state, never mid-flight, because the runner can hand a job one more attempt than its budget.
- **Chains** — `enqueue_chain(steps)` creates every step at once as one entry of the queue of each target it touches, and hands them to queue_job as an OCA DelayableChain when their turn comes. Payloads may reference earlier steps with `__chain_job_N__` placeholders (0-indexed), resolved to real job ids at dispatch. When a step fails or is cancelled, the steps after it in its `queue.job` graph that still wait in `wait_dependencies` end `cancelled` at both the `cloud.job` and `queue.job` level, with a note in their log ("Not run: step #N ended failed."): only the step that failed is a failure, and a step that never ran offers no retry. Only the chain's own graph is ended — a chain can cross instances (a staging built from production takes its dump on production), and a probe failing beside it ends nothing of it.
- **Cancel** — `cancel_job` holds a job, in whatever state, to the role gate `enqueue` holds its type to, and so every job the cancellation ends with it: the rest of a chain waiting in the queue, or the steps waiting on a dispatched or running one. One of them the caller may not ask for refuses the whole cancellation, before anything ends: stopping the step that heads a manager's move would end the move. The caller must also be able to write the job. A job waiting in its target's queue (`queued`) is cancelled on the spot: nothing runs and nothing reaches the host. A dispatched job that has not started is cancelled through queue_job, with `sudo()` (no role of the panel reads `queue.job`); a started job gets a cooperative cancel flag that the executor polls between commands on a separate cursor, and stops: what it leaves is closed as a failure would close it (`on_cancelled_running`), with no alert raised. The job then ends `cancelled`, also when storing its end collides with the flag's own write and queue_job would otherwise put it back in the queue (`queue_job_ext.write`). Not when its `on_success` had returned: the flag's write still makes the store of `done` fail to serialize, so the executor marks the job, on a cursor of its own, `succeeded_before_cancel` (only a job already cancelled: on any other, that write would make the store fail), and `queue_job_ext.write` stores it `done` — never `cancelled`, nor `pending`, which would run it again — and sets the next steps of its chain going (6-nov-2026: a cutover that had cut over ended cancelled, and so did the freeze of its source). The mark is taken again at the very end of the run, so a stop committed while the staging was discarded or the transport closed is marked too; only one committed after the run returned, before the store, still ends it cancelled. A job whose worker died after the stop and that queue_job puts back in the queue keeps `cancelled`, and the mark, when it starts again, and does not run (below). The job's own transaction was rolled back, and with it the unlink a delete's or a purge's `on_success` leaves for its commit: `queue_job_ext` arms that unlink again on the cursor that stores the job `done`, and sets the next steps going with the savepoint and retries queue_job gives them. An executor of a layer that calls `on_success` or `on_failure` itself, outside `_dispatch_outcome`, has none of this: the flag is read while its hook runs, and its success is not marked (pending a decision).
- **A worker that dies** (6-nov-2026). queue_job finds a job whose worker died by its released lock (`requeue_dead_jobs`, every pass of the jobrunner): it puts it back in the queue (`pending`, one more retry), or, past `max_retries` (1 for a `cloud.job`: three deaths), fails it `JobFoundDead`. Both are one SQL `UPDATE`, which `queue_job_ext` never hears of, so the cloud job stayed `started` for good: its queue busy (`_scope_busy`), `job_running_too_long` raised forever, its move never rolled back (`cron_recover_stuck_moves` saw a step in flight), the steps after it waiting forever. Causes seen: the runner's 60-minute kill, `limit_memory_hard`, a restart of `odoo_runner` in a deploy, a server that went down.
  - **The reconciliation** (`cloud.job._cron_reconcile_lost_jobs`, every 5 minutes, `data/job_reconcile_cron.xml`) reads, without locks and 20 at a time, the dispatched jobs whose two rows disagree: active with a `queue.job` failed or gone (closed `failed` after `on_abort(JobWorkerLost)`, with its `job_failed`); `cancelled` with a `queue.job` found dead (a stop whose worker died: closed `cancelled` after `on_cancelled_running(None, …)`, no alert; `done`, with no hook, when its `on_success` had returned); started with a `queue.job` cancelled (`on_cancelled_running`, closed `cancelled`); dispatched and not started with a `queue.job` cancelled (closed `cancelled`, which gives it `on_never_run`); active with a `queue.job` done (closed `done`). A `cancelled` job whose `queue.job` is gone is history (the autovacuum deletes them after 30 days), and a job whose `queue.job` waits or runs is queue_job's, however long it takes: whether a worker is dead is its lock's to say, never a clock's. Both rows must have stood still for 2 minutes (`_RECONCILE_GRACE_MINUTES`), for what may still be in flight: an ORM transition writes both in one transaction.
  - **Three steps, each on a cursor of its own, at most one clean-up.** Claimed: both rows locked `FOR NO KEY UPDATE SKIP LOCKED` (`cloud_job`, then `queue_job`: nothing waits, so no order of locks can deadlock), the case read again on them, `worker_lost_at` set and committed; a row someone holds is left for the next pass. Cleaned up, with no lock held: a new executor, as the job's creator (`_as_its_creator`, the environment `_dispatch_single` gives a run), gets the hook of the case on a durable cursor (`_dispatch_abort` / `_dispatch_cancel`, which never raise), then the job log says what happened and its watchers hear of it. Closed: locked again, and the end the ORM never saw is written through `queue.job.write` (or, its `queue.job` gone, the job's own write, `job_failed` and `_on_state_changed`), so the mirror, `job_failed`, the end of the chain (its next steps `cancelled`, their `on_never_run`), the queue and the bus come as for any end. A job claimed and not closed (the cron died between the two) is only closed on the next pass, and its log says the clean-up may have stopped half way; a requeue by hand after a claim clears `worker_lost_at` when the job starts again. A pass starts no further clean-up once 60 s have gone by (`_RECONCILE_HOOK_BUDGET_S`): a hook may wait on a host or a provider, and the pass holds the runner's cron thread; the first one always runs, the rest are the next pass's. With the jobrunner the sets never meet: `requeue_dead_jobs` touches `enqueued`/`started` rows, the reconciliation ended or missing ones; a `cancel_job` between the claim and the close is turned into the stop by the close (`queue_job_ext`), after the one clean-up already done.
  - **A stop is not run again.** A job a person cancelled whose worker died before it stopped goes back to the queue still `cancelled`: the mirror of `started` used to write over the flag, and the job ran again from the start with no hook. The mirror now leaves it `cancelled` (with `succeeded_before_cancel`), and `execute` reads the flag before anything (`_check_cancel`, before `pre_run_checks`): the job does not run, `on_cancelled_running(None, …)` puts back what its lost run left — the hook the reconciliation gives a stop — unless its `on_success` had returned, and the stop is stored as ever (`cancelled` and its chain ended, or `done` and its chain going on).
  - **Hooks on an executor that knows nothing of the run** (reviewed 6-nov-2026). The clean-up's executor is a new one: what the lost run kept in memory (`_step_results`, a PITR restore's `_plan` and `_rejoined`, a VPS purchase's `_vm_id` and calls in flight) is not there, only what the database holds. Core's overrides: `deploy_instance` and `capture_secret_key` (`on_abort` → `on_failure({})`: the instance in error and back to draft; the key not escrowed, a warning), `delete_instance` (by the instance's state: in `deleting`, its failure — in error and back to `deployed`, the next delete runs the teardown again; else the log), `full_setup` (by the server's status: in `checking`, its failure; else the log), `rebuild_instance` (`on_abort` writes the log; `on_cancelled_running` below, reads the steps from the job log), `move_freeze_source` (`on_cancelled_running` → `on_failure({})`: the old copy recorded frozen, with its alert), `host_probe` (the log): all read the database alone and are sound on a new executor. `pitr_enable` (`on_abort` → `on_failure({})`) asks the host to settle archiving (`pitr.sh settle`, on a connection of its own) and sets `pitr_state` and `pitr_failing` from its answer; a host that does not answer leaves a critical alert, as the database may be keeping its log. `pitr_restore` asks the host (6-nov-2026, see *Cancelling a restore* under [Continuous recovery](#continuous-recovery-incubacloud_pitr)): `on_cancelled_running` always, with `restore-cancel`; `on_abort` when the run never heard from it (no `_plan`, no `follow`, `_probed` unset), with `restore-wait <job> 0` — a restore still running is followed by the next job, one that ended is recorded as its wait would have, and nothing is done when no restore of the job is there. An executor that buys a server frees, in its `on_cancelled_running`, the server whose id it persisted; one created and not yet written down when the worker died is not known to a new executor.
  - **What it assumes and what it leaves.** The panel's database must not cut idle transactions (`idle_in_transaction_session_timeout` off): a job's transaction is idle while its SSH steps run and a durable hook waits (a PITR restore's, minutes), and cut off, its lock is released and queue_job takes a live job for dead. Production, 6-nov-2026: `0`, the default, and no role or database sets it. A worker that dies inside `on_success` on its last attempt is closed failed and `on_abort` runs over a success already written (a deploy marked in error): it takes the third death at that very point, and is accepted. A step `done` whose worker died before queue_job set the next one going (`_enqueue_dependent_jobs`) leaves that one in `wait_dependencies`: not handled here. A job that dies is still run again from the start, twice, before queue_job gives up: that is queue_job's.
- **A success is not run again** (1.0.217, 8-nov-2026). `on_success` commits on its durable cursor before the runner's transaction stores `done`. When that store then fails to serialize — queue_job runs the whole job again 5 s later, outside `max_retries` — or the worker dies before the commit, the next attempt used to start from `execute` in a world where the job was done: a cross-host restore looked for the handoff its first success had removed, failed, and its move was rolled back (7-nov-2026); rebuilds built and restarted twice. Now the success hook's last statement, on its own cursor, inserts a `cloud.job.outcome` row (the job, its `queue_job_uuid`, what `_write_own_job` wrote — `own_job_vals` — and what the hook left for the job's commit — `owed`, today the unlink of a deleted or purged instance). Only `on_success` leaves one: a failure, or `on_failure` followed by a `RetryableJobError`, runs again as before. `cloud.job.execute` reads the row first, before the stop flag and `pre_run_checks`, in the attempt's own transaction, which began after that commit: when it is there the attempt connects to nothing, writes `own_job_vals` again on the job's row, arms what is `owed` for its own commit (`_rearm_owed`, decided on a fresh read: `queue.job._unlink_owed_instances`), logs why and returns `ALREADY_DONE`. `queue_job_ext.write` reads it on a fresh cursor too (the runner's snapshot predates it): a job stored failed, with the stop's result, or put back in the queue (the store of `done` lost its race, against a stop that came after the mark or anything else; on the temporary cursor of queue_job's `retry_postpone`) after its success committed is stored `done`, with its own row written again, what it owed armed again and the steps after it set going — read as the stop alone, a stop after the mark ended it `cancelled` and cut its chain. The reconciliation of lost jobs closes a job whose mark is there `done` the same way (`succeeded`), with no `on_abort` and no `on_cancelled_running`: a worker that died after the hook's commit no longer has its success undone; one whose queue.job is gone is closed `done` with its own row written again, and what it owed is not armed (that goes through the queue.job). Not covered: the executors of a layer that call `on_success` themselves (a VPS purchase, the PITR restore's follow-up), and a worker that dies in the middle of the steps — each type's own idempotency (`tests/idempotency_harness.py`).
- **The store of `done` writes only the job's rows.** It began before the job's hooks committed on their cursors, and any row they — or the metrics cron — changed since makes PostgreSQL refuse its commit: queuing the instance's state probe (a `cloud_job` whose key locks the instance's row) was the likely trigger of the 7-nov repetitions. So the runner's store of `done` updates `cloud_job` and `queue_job` and nothing else; after its commit, each on a cursor of its own (`_concurrency.run_after_commit`, which logs what a callback raises instead of letting it reach the runner): the bus event, the mail, Telegram and webhook of a success (`_announce_done_after_commit`), the dismissal of earlier failures, the autopurge clock, the layers' `_after_job_terminal` (`_run_after_terminal_after_commit`, with `ic_after_job_commit` in the context) and the instance's state probe (`_refresh_instance_state`, also after a failure's commit), then the queue's dispatch. A store that does not commit announces nothing; a worker that dies between the commit and these loses them, and the log does not show it. What it does not prevent: a job that wrote its own row in its transaction (`_write_own_job`) updates that row a second time when it is stored, and PostgreSQL checks its keys again; when the metrics cron locked the instance's row `FOR UPDATE` and wrote it meanwhile (`cloud_instance_metrics`), that check is refused and the store fails as on 7-nov-2026 (`test_job_outcome_real_cursors` reproduces it). The outcome mark makes the attempt that follows harmless; the cause goes once that cron's lock is `FOR NO KEY UPDATE`.
- **A job that runs in ticks** (`_postpones_between_ticks` on its executor, such as an order that waits on a provider). A stop committed between the tick's own read of the flag and the store of its postpone is stored as the stop (`queue_job_ext.write`), and reached no hook: with the flag set, its `on_never_run` lets go, as for a job cancelled between two ticks. The hook must then do nothing a second time.
- **Cross-host move** — `cloud.instance.move_to_host(target_host, move_options=None)` queues one chain across both hosts, run whole when the move is due (a destination prepared days before would restore a database newer than its code once a release ships, and hold capacity twice): deploy(target, **no database**: the deploy skips «Start database», «Initialize database», «Initialize module checksums» and «Set system parameters», `_move_skipped_labels`, but pulls and starts every container) → stop `odoo` (target) → [prepare steps] → `move_quiet_check`(source) → [pre-steps] → stop `odoo` (source, `move_cut`: stamps `move_cut_started_at`, the cut starts) → [cut steps] → `move_fingerprint`(source) → live dump of the stopped database with its filestore (`backup_download`, `time='live'`, staged on the source) → restore(target, fetched through the panel's disk, `verify_job` = the fingerprint, loaded with `--move`: the same database keeps its `database.secret`, so the links it signed stay valid, its `database.uuid` and its `web.base.url`; sessions are not carried, they live in the data dir's `sessions/`, outside the archive, so users sign in again) → [post-restore steps] → `move_cutover`(target) → `move_freeze_source`(source) → [freeze steps]. It needs no backup container and no bucket. `move_options` travels in the payload of the quiet check (`_last_move_options`); its `trigger` (`idle`, `window`, `now`, or `manual` when missing) says what started the move.
  - **Postponed, not failed.** `move_quiet_check` runs before anything on the source changes. Busy is a job of the panel running on the instance besides the move's own, or a count above zero from the SQL a layer gives (`_move_quiet_sql`, run in the instance's database by `move_steps.sh quiet`), or, for the triggers a layer reads, recent requests (`_move_requests_check(trigger)`). A count inside the instance that could not be read postpones the move as `unknown` rather than failing it. A busy instance ends the step `done`, writing nothing on its own job, and `_postpone_move` hands what it found (`reason` — `busy`, `active`, `unknown` —, `detail` and the move's `trigger`) to the outcome, cancels the rest of the chain and takes the destination down with a `move_rollback_cleanup` marked `move_postponed`: no `start_instance` on the source (it never stopped), no `job_failed`, no `move_stuck`.
  - **A step's own job row.** The hooks of a step run on a durable cursor that commits before the job's transaction stores it `done`; a hook that wrote the job's own `cloud_job` row there made that store fail to serialize, and queue_job ran the step again for ever. The one value a step keeps on its job, the fingerprint, is written by `AbstractExecutor._write_own_job`, in the job's own transaction and flushed (`test_move_own_job_row` runs it on two real transactions).
  - **Integrity.** `move_fingerprint` counts, with the source's Odoo stopped, the rows of `_move_fingerprint_tables` (small tables only; core: `res_users`, `ir_config_parameter`, `ir_attachment`; a missing table is skipped) and the files of the filestore. The restore counts them again between «Restore database» and «Start Odoo service» (`move_steps.sh verify`) and fails on any difference, naming the table and both counts, before Odoo starts on the destination: the chain stops before the cutover and the move is rolled back.
  - **The cut, measured.** From `move_cut_started_at` to the destination answering healthy in `move_cutover`: `move_last_cut_seconds` on the instance, in its log («The instance was unavailable for N s»), and passed to the hook. Over `cloud.settings.move_cut_alert_seconds` (90) the cutover raises `move_slow_cut` (warning); a later cut under it resolves it.
  - **The old copy is frozen.** `move_freeze_source` stops every container of the source's stack with its restart policy set to `no` (a host reboot must not start it beside the moved instance), keeps its directory and volumes, and sets `move_frozen_source_host_id` and `move_frozen_until` (`move_frozen_source_hours`, 48). `move_cleanup_source` removes it later: the hourly `cron_clean_frozen_move_sources` once its time is up, a new move of the instance (queued ahead of its chain, whichever host it goes to), the instance's delete or archive (queued ahead of them), or the instance's «Clean frozen copy now» (`action_clean_frozen_copy`). A copy on a host archived, out of service or no longer compatible is forgotten with an audit entry. A move back to the copy's host never starts it: the deploy of that destination refuses while the copy is still recorded there (the removal failed), and the move is rolled back. A freeze that failed records the copy all the same, for the clean-up, and raises `move_freeze_failed`. There is no automatic way back: the copy is the operator's, for a manual restore.
  - **Capacity.** A moving instance counts on its destination (`move_target_host_id`) as well as on its host until the cutover.
  - **Priority.** `cloud.instance.scheduling_priority` (`low`/`normal`/`high`) sets `cpu_shares` 512/1024/2048 on `odoo` and `db` in the resource override, and at `high` a `mem_reservation` of half `mem_limit`.
  - `host_id` flips only on a successful cutover; a watchdog cron recovers instances stranded by a chain that died before the cutover (restarts the source, raises `move_stuck`), and `rollback_move` does the same on demand. The record stays `deployed` throughout: the deploy on the target does not touch its state during a move. Hooks for an inheriting layer: `_move_deploy_job_type`, `_move_prepare_steps(source)` (before the quiet check: what takes time and a postponement's rollback hook undoes), `_move_pre_steps(source)` (right before the source's stop, once the quiet check passed), `_move_cut_steps(target)` (as the cut starts), `_move_post_restore_steps(target)`, `_move_freeze_steps(origin)`, `_move_quiet_sql()`, `_move_requests_check(trigger)`, `_move_fingerprint_tables()`, `_on_move_cutover(origin_host, cut_seconds=None)` and `_on_move_rolled_back(target_host=None, outcome=None)`, fired once a rollback has cleared the markers, with the `outcome` read before: `kind` — `postponed`, `failed`, `cancelled`, `manual` or `stuck` — and, when known, `reason`, `detail`, `trigger`, `job_id`, `job_type` and `message` (`_move_outcome`).
- **Blocked deploys** — a deploy whose repositories define an addon twice waits on one `addon_conflict` alert instead of failing, and leaves the instance in `draft`; resolving the alert, or a repository save that leaves no conflict (`_check_addon_conflicts`, also run after an import; a repository GitHub would not list closes nothing), puts it back in the instance's queue, in the place its creation gives it, on the host the instance is on by then, and cancels the other jobs of its type waiting on the instance; a deploy or rebuild that goes through cancels those that waited on the alert it closes. Only a job nothing runs after waits: a step of a chain fails. A job whose failure its own critical conflict alert explains raises no `job_failed`, and queue_job's own failure message is left out for platform jobs.

### The job queue

An instance runs one visible job at a time, and a host one host-level job at a time (a job with no instance). The two queues are independent: a deploy does not wait for a host probe, nor the other way round. Asking for a job while another runs on the same target is never refused for that reason: `enqueue` and `enqueue_chain` always create the record, and the job waits.

- **`queued`.** `cloud.job.state` is the job's own stored field, not a mirror of `queue_job_id.state`: a job waiting in its target's queue is `queued` and has no `queue.job` yet. Once dispatched it follows its `queue.job`, which `queue_job_ext` writes back on every transition the runner makes through the ORM (`pending`, `started`, `wait_dependencies`, `done`, `failed`, `cancelled`); `enqueued` is written by SQL and never arrives, so a dispatched job shows `pending` until it starts. `_active_states` includes `queued`; `_running_states` (dispatched and not ended) does not. A job waiting for an alert (`blocked_alert_id`) shows as `blocked` either way, but is stored in one of two ways: blocked when it was asked for (`enqueue` found a dependency or addon conflict) it has no state and no `queue.job`; blocked by its executor (`blocking_alert`, `cloud.job._block_on`) it ran and ended `done`, with `blocked_alert_id` set. Resolving the alert puts it back in the queue (`unblock_and_enqueue`). The 1.0.198 migration ended `cancelled`, with a note, the jobs left with an empty state when their `queue.job` was deleted.
- **Order.** First come, first served, by creation (`_queue_entries`), with no priority between types. What the running job queues for itself — `bypass_running_check`, now meaning "I am part of the job running": an executor's `on_success` chaining a follow-up, a move's rollback jobs, the PITR chain a rebuild queues — goes to the head (`queue_head`), before everything waiting, heads among themselves by creation. Only the platform may ask for it: `enqueue` and `enqueue_chain` are reachable through `call_kw`, so a caller without superuser rights who passes it, or `move_rollback` in a payload, is refused (`AccessError`, `_check_internal_queue_flags`); the platform's own callers ask for it with `sudo()` (a cron runs as its bot, without superuser rights, and an executor's job runs with them only when it was asked for with them). Such a caller is refused, too, a target they cannot read — an instance of a project they are not in — before its queue is looked at (`AccessError`, `_check_target_access`): collapsing into a waiting job, merging a push into a waiting rebuild and the queue's refusals all read the queue with `sudo()`, and would otherwise answer with another project's job, write into it, or tell what waits there. A step of a chain on an instance must name, too, the instance's host or, while it moves, the move's origin or destination (`AccessError`, `_check_step_host`): the dispatcher puts a lone job where its instance is, but a chain's steps keep the hosts they name, and `cloud.host` has no record rule. Nor may such a caller create a job, or write what the dispatcher and the executor read — the state, the head, the chain, the retry, the blocking alert, the queue.job, the type, the payload and its secret, the instance and the host, the rights it runs with and when it ended (`_QUEUE_CONTROL_FIELDS`) — with `create` or `write` (`AccessError`, `_check_queue_control_vals`): a job is queued, retried, unblocked and cancelled only through `enqueue`, `enqueue_chain`, `retry_job`, `unblock_and_enqueue` and `cancel_job`, with their checks. They write those fields with `sudo()` once the caller's own access to the job is checked, record rules included (`_create_queued` for the new ones), so the caller stays the job's creator (`create_uid`, as whom `_dispatch_single` runs it); and only a job waiting for an alert can be unblocked. `execute`, which queue_job calls by name, is private (`@api.private`): through `call_kw` anyone who reads a job would run it again outside its queue. So are `unblock_and_enqueue` (it would queue a job past the alert it waits for, still open), the backup cleanup cron's method and `get_audit_log` (served by its own route). The retry of a failed job goes to the head too.
- **Chains are one entry.** The steps of `enqueue_chain` share a `queue_chain_key`, wait whole and count once towards the cap and towards "N ahead". A chain that touches several targets (a clone to staging: deploy on the staging, download on production, restore on the staging) waits in the queue of each, is dispatched only when every one of them is free and it is first in each, and occupies all of them until its last step ends. What is queued meanwhile waits for that last step. Cancelling a waiting chain cancels every step.
- **What the type says** (`cloud.job.type`, set in the data files of the module that declares it). `queue_collapse`: asked for again while an identical one waits — same type, target, payload and secret (`_queue_identity`; a layer that keeps credentials in `secret_payload` gets two pushes differing only there as two jobs) — the waiting job is returned instead of a second one; a job already running is never collapsed into. `queue_exclusive`: one at most may wait on a target, whatever its payload ("A Restore Database is already queued for this instance; cancel it first."). `failure_holds_queue`: a failure holds the target's queue (below). The types are judged as the layer finally routes them (a layer that turns a rebuild into a rebuild of its own does so before the rules apply). A rebuild asked for by a GitHub push merges into the rebuild of a push already waiting instead (`RebuildInstanceExecutor._merge_queued_payload`, see [Webhooks and auto-rebuild](#webhooks-and-auto-rebuild)).
- **Five at most.** A queue holds `QUEUE_MAX_WAITING` = 5 entries; the sixth is refused ("The instance has 5 jobs waiting in its queue."). Heads, retries and merged pushes are not counted and not refused.
- **A failure holds the queue.** While a failed job of a type with `failure_holds_queue` has its alert active — the `job_failed`, or the critical conflict alert (`pip_conflict`, `addon_conflict`) that `_create_job_failed_alert` raises instead — nothing behind it is dispatched (`_queue_held_by`), and the lists show the waiting jobs as "Action required", with the way to the alert (`queue_held`, `queue_held_alert_id` in `_format`). The queue is released when that alert closes: a retry that ends `done` resolves it, or someone dismisses it (`cloud.alert.write` → `_on_holding_alert_closed`). The retry passes the hold and goes to the head; one retry per failed job may wait or run at a time. A delete of the instance (below) and the jobs of a move's rollback — marked `move_rollback`, while the instance's rollback is in progress: the failure is usually the step it rolls back — pass the hold too (`_passes_hold`), and the lists do not show them as held. So does the rebuild of a GitHub push after rebuilds that failed (`_supersedes_hold`, `RebuildInstanceExecutor._supersedes_failure`): when every failure holding the queue is a lone rebuild of the same type, asked for by a push or by hand, with its `job_failed` and no conflict alert open on it, a push's rebuild carrying a commit none of them was asked for (`push_sha`, merged pushes included) is a new attempt, not something that would only fail behind them. The same push delivered again, a rebuild asked for by hand and a retry of an older failure do not pass that way; a conflict, a failed deploy, restore or move step, or a failed step of any chain keeps holding. None of them closes the alert: a success of the rebuild that passed resolves it (`resolved_by_job_id`), and a failure refreshes the same `job_failed`. Cancelling the failed job releases nothing — a failed job cannot be cancelled. A failure of a type without the flag holds nothing: the next job starts. `move_cleanup_source`, the last step of a move, has no flag: it runs after the cutover, when the instance already lives on the destination, and a failure to remove the old copy from the source must not stop the instance's backups and jobs; its alert and its retry stay.
- **A delete empties the queue.** Enqueuing `delete_instance` (and the types a layer adds through `_get_queue_clearing_job_types`, such as a delete of its own) first cancels everything waiting on the instance ("Cancelled: the instance was asked to be deleted.") and then waits only for the job running; it passes a held queue too. Whoever asks for it must be able to stop all of that, each job with the rest of its chain, as `cancel_job` would hold them to it (`_check_may_end_waiting`): a consultant may not end that way a developer's restore or a manager's move waiting on a staging, and the delete is refused whole, before anything ends, naming the job. Archiving an instance, whose waiting entries the dispatcher then cancels, and removing its record, which cancels them at once, are held to the same; the delete's own end archives or removes the record as the platform, since what waits behind it was asked for on an instance being removed. An archiving or a removal judges what this transaction's snapshot sees, without the queue's lock that a delete holds: a job asked for at the same moment is not judged, and ends as one asked for on an instance being removed would. `/cloud/delete_instance` no longer refuses while jobs are active.
- **Cancelled before it started.** A job or chain cancelled while it waits — by a person, by a delete, by its instance being gone — is cancelled at once, with a note, and its executor's `on_cancelled_queued` puts back what was written when it was asked for (a deploy's instance back to `draft`, a move's markers cleared), in the canceller's transaction. Then `_after_job_terminal("cancelled")` runs for the layers. A job that left its queue but will never run — a step of a chain that a step before it ended, or a dispatched job cancelled before it started — gets its executor's `on_never_run` instead (`queue.job._end_chain_after`), which keeps what was written when it was asked for and only lets go of what the steps that ran left for it on a host: a `from_host` restore queues the hidden `discard_handoff` on the download's host, and a deploy puts its instance back in `draft`, as nothing of it reached the host. Neither hook reaches a host itself: they run in the transaction that records the end, sometimes with the queues' locks held.
- **Checks at dispatch** (`_entry_verdict`). An entry whose instance no longer exists, or is archived when its type is not meant for archived instances (`_runs_on_archived_instance` on the executor, e.g. the purge of an archived instance's backups), is cancelled ("Cancelled: the instance is no longer there.") and the next one is looked at. A lone job goes where its instance is now: a move between queueing and dispatch is followed (a chain's steps keep the hosts they name, which a caller without superuser rights chooses only among the instance's host and its move's: `_check_step_host`). Not a job whose executor runs on the host it was asked for (`_pinned_to_host`: a move's two teardowns and its cutover, an upload grant's jobs), which keeps that host, in its retries too: sent where the instance lived, a rolled-back move's cleanup removed the copy on the source (28 October 2026). The move's teardowns also refuse, before they connect, a host the instance lives on or is moving to. The other queues of a chain are only tried for (`pg_try_advisory_xact_lock`), never waited on, so two dispatchers cannot deadlock on each other.
- **Locks.** Whoever enqueues, dispatches or cancels on a queue takes its PostgreSQL advisory lock first (`_lock_scopes`, one namespace for instances and one for hosts, in a fixed order), so two of them cannot both find the target free.
- **The dispatcher runs after the commit, on a cursor of its own.** The end of a job, a cancellation, a holding alert closed, an unblock and a retry register a dispatch of every queue concerned on `cr.postcommit` (`_schedule_dispatch`, once per queue and transaction); it runs on a fresh READ COMMITTED cursor, as the platform (`_dispatch_scope_fresh`). Odoo's cursors are REPEATABLE READ: the runner that ends a job reads the snapshot it took when the job started, and would not see what was queued during the run. Whatever goes wrong there is logged and never changes how the job that ended is stored; a layer's `_after_job_terminal` runs in a savepoint for the same reason. The jobs it starts run as their creator (`_dispatch_single`), possibly long after they were asked for, with superuser rights only when they were asked for with them (`asked_as_superuser`, set from the caller's environment by `enqueue` and its siblings, by `unblock_and_enqueue` from the one who sets a blocked job going), as until 1.0.197, when `enqueue` handed queue_job the caller's own environment: a consultant's job runs under their record rules — a restore reads the job it takes its data from as its creator may — and what the platform's code asked for with `sudo()` (an executor's follow-ups, the website's flows, a cron that elevates) runs as the superuser. A job waiting for an alert runs as its creator too, with the rights (superuser or not) of whoever sets it going; until 1.0.197 it ran as them. The dispatcher's own writes, the uuid and the state, are the platform's. `enqueue` dispatches in the caller's own transaction only its own new job, and only when the target is free and nobody waits both in its snapshot and in a fresh READ COMMITTED read — so two requests at the same moment do not start two jobs. The exclusive rule, the cap and the one retry per failure count what this transaction's snapshot sees plus what only the fresh read sees (`_fresh_only`: jobs whose ids the snapshot does not know at all), so a delete is not refused by the jobs it has just cancelled, which the fresh read still sees waiting; collapse and merge read the snapshot alone (in the rare race of two identical requests committing at once, the second queues a duplicate).
- **The sweep.** `cron_job_queue_dispatch` (`_cron_dispatch_queued`, every 2 minutes) serves every queue that waits with nothing running and nothing holding it, one fresh cursor per queue: a dispatch lost to a rollback or to a path nobody hooked starts within two minutes.
- **Who reads a busy target.** Everything that asks whether an instance is busy counts a waiting job as busy: the host endpoint guard, the PITR checks, the docker prune's per-instance check, the hardening preflight (`has_active_job`). The move watchdog counts a waiting job only when it is a step of the move or of its rollback: one asked for after the failure waits behind its hold, and would keep the source stopped for as long. The health probe does not — a job that has not started silences nothing — and `/cloud/get_backup_result` treats a queued listing as waiting, not as an error.

### Implementing a new executor

Executors self-register: subclassing `AbstractSSHExecutor` with a `_job_type` adds the class to the registry (`models/registry.py`) automatically. The code must match a `cloud.job.type` record.

```python
from odoo.addons.incubacloud.models.abstract_executor import AbstractSSHExecutor

class MyExecutor(AbstractSSHExecutor):
    _job_type = 'my_job_code'  # must match cloud.job.type.code

    def get_commands(self):
        return [
            ('step_1', 'echo hello'),
            ('step_2', 'uptime'),
        ]

    def parse_results(self, results):
        if results['step_1']['exit_status'] != 0:
            return ['step_1 failed']
        return []

    async def on_success(self, results):
        # runs in a fresh DB cursor after all commands succeed
        instance = self.job.instance_id  # cloud.instance record
        # ``deployed`` is DERIVED from the lifecycle state and cannot be
        # written: cloud.instance.write() rejects both 'deployed' and
        # 'state'. Move the instance with _transition(), which validates
        # the move against the transition map, and write only the plain
        # fields alongside it.
        instance.write({'running': True})
        instance._transition('deployed')

# Commands can include a third element for options:
def get_commands(self):
    return [
        ('build', 'docker compose build odoo', {"stop_on_failure": True}),
        ('test', 'docker compose run --rm odoo odoo --stop-after-init'),
        ('restart', 'docker compose up -d'),
    ]
# If 'build' fails, 'test' and 'restart' are skipped.
```

### Transaction model

**The job's transaction is not written.** An executor runs inside the transaction `queue_job` opened for its job (which holds the lock on the `queue.job` row), and nothing written there through `self.env` can be relied on:

- `cloud.job.execute()` ends with `env.clear()`, which in Odoo 18 and 19 drops every write not flushed yet. Core 1.0.135 started VictoriaMetrics with a deletion key the database never received that way.
- `queue_job` rolls the whole transaction back when the job fails or is retried, and refuses a commit midway (it would release the job's lock).
- A write that does get flushed holds its row until the job ends; a hook writing the same row on its own cursor then waits for a transaction that is waiting for the hook.
- The transaction is REPEATABLE READ and its snapshot dates from the job's start, so a value committed on another cursor stays invisible to it — invalidating the cache and reading again returns the old value (measured).

Two primitives on `AbstractExecutor` cover every durable write:

| Primitive | Use it for |
|---|---|
| `with self._durable_env() as env:` | Writes that must last. A fresh READ COMMITTED cursor, committed on exit and rolled back if the block raises; the lock wait is capped at 30 s, so a mixed-transaction deadlock becomes an error instead of a stuck worker. Same user, superuser flag and context as the job. |
| `self._persist(record, vals)` | A durable write the rest of the job must also *see*. Writes through `_durable_env()`, then copies the committed values — and the stored computed fields of the same record that depend on them — into the job's cache. |

`on_success` / `on_failure` / `on_abort` / `on_cancelled_running` already run inside `_durable_env()` (see `_dispatch_outcome`, `_dispatch_abort`, `_dispatch_cancel` and `_as_durable`) and write with `self.env`; `on_success`'s cursor also writes the job's outcome mark, last (`cloud.job.outcome`, see [Reliability guarantees](#reliability-guarantees)). `pre_run_checks`, `before_execute`, `get_commands`, `get_extra_vars`, `after_commands` and `parse_results` do not. The one write that waits for the job's own commit is `_unlink_after_job_commit`; it is noted in the mark, so an attempt that finds it arms the unlink again.

Two exceptions write the job's own transaction, on purpose. `blocking_alert` and `on_blocked` run there when a job ends blocked: it ends without an error, so that transaction commits, and `cloud.job._block_on` flushes it before `execute` clears the environment. For a step of a chain, which cannot wait and fails instead, `execute` runs `blocking_alert` inside `_as_durable()`, so the alert outlives the rollback. `on_unblocked` runs in the transaction of whoever resolved the alert.

```python
# Durable; invisible to the rest of this job (alerts, logs, state for a retry):
with self._durable_env() as env:
    env['cloud.alert'].raise_alert(...)

# Durable AND read again later in this job (the upload step reads it):
self._persist(inst.sudo().with_context(pip_provenance_managed=True), vals)

# WRONG — dropped at the end of the job, or taken back if it fails:
self.env['cloud.instance'].browse(inst_id).write({...})
```

A model helper meant to be called from an executor writes through the environment of the record it is called on, so the executor can bind it to a durable one (`env['cloud.settings'].sudo()._get_system()._ensure_operator_credential()` inside `_durable_env()`); it never opens a cursor of its own.

**Enforced by tests.** `tests/idempotency_harness.py` runs a job type through `cloud.job.execute` once, twice after a lost commit, and cut off (a `BaseException` of its own) after each call to a host and at the end of `on_success`, and compares what each leaves and which calls that must happen once did; every registered type of a repository has a specification or an exemption with its reason (`test_job_idempotency`, in core and in each repository built on it). `test_job_outcome_real_cursors` reproduces the lost store on real cursors. `tests/executor_write_rules.py` checks every executor class of core and of the repositories built on it by AST: no cursor opened outside `abstract_executor.py`, and no `write` / `create` / `unlink` / `_transition` / `enqueue` / `raise_alert` / … outside a durable block or a hook (a short, verified list of hook-only helpers aside). It cannot see a write made inside a model helper; `tests/test_executor_durable_writes.py` covers those by ending the job the way the runner does (`env.clear()`) and reading the row by SQL — the check the 1.0.135 test was missing. In a `TransactionCase` the durable cursor rides on the test's own transaction (`registry_enter_test_mode()`), so the REPEATABLE READ snapshot cannot be reproduced there; it was measured with two real cursors.

**Rows are locked `FOR NO KEY UPDATE`.** A `SELECT … FOR UPDATE` followed by an `UPDATE` of the row in the same transaction marks the tuple as a change of its key; any REPEATABLE READ transaction begun before that commit that then inserts or updates a row with a foreign key to it fails to serialize, because its key check (`FOR KEY SHARE`) meets a key it believes changed. A move failed so on 7-nov-2026: the probe of running panels (`_running_confirmed_after`) held the instance `FOR UPDATE` and wrote it, and the store of `done` of the move's job, keyed on that instance, failed. `FOR NO KEY UPDATE` (`lock_for_update(allow_referencing=True)`) excludes the same writers and conflicts with itself, so `SKIP LOCKED` still skips a row another such lock holds, but lets the key check through. That holds only while the write leaves the key alone: for PostgreSQL the key is every plain column of a unique index that is not partial (deferrable or not), and an `UPDATE` that changes one is a change of the key whatever lock came before, or none. Measured on 8-nov-2026: `FOR NO KEY UPDATE` + another column passes, `FOR NO KEY UPDATE` + `project_id` (in `cloud_instance_name_project_uniq`, `UNIQUE (project_id, name)`) fails, no lock + `project_id` fails. A layer whose write moves an instance to another project still fails such a transaction. `FOR UPDATE` is kept for a row about to be deleted or to change a column of a unique index, marked `# lock: key-update needed — <why>`. `tests/row_lock_rules.py` scans every addon of a repository (tests and docstrings aside) for `FOR UPDATE` and for `lock_for_update()` / `try_lock_for_update()` without `allow_referencing=True`; core and each repository built on it run it. `test_running_probe_lock_real_cursors` reproduces the failure with real cursors.

Bus notifications go out from durable cursors too (`_publish_bus`), and only **during** execution. PostgreSQL `NOTIFY` is committed automatically with the transaction.

## Safe rebuild

Rebuilds verify the new Docker image before applying it to the running instance. The flow:

1. `docker compose build --pull --no-cache odoo` — builds the new image (`stop_on_failure`)
2. Clone the production DB via `createdb -T` (instant copy using PG hard-links)
3. Run `click-odoo-update --database __ic_boot_test` against the clone
4. Drop the test DB (`dropdb --if-exists __ic_boot_test`) — always runs, even on failure
5. If the test passed, update the real DB and restart with `docker compose up -d`
6. If the test failed, `stop_on_failure` aborts — the instance keeps the old image

The clone requires terminating active connections first (`pg_terminate_backend`). Odoo reconnects automatically. The boot test runs against the instance's own Postgres image (pgvector-enabled), so extension-dependent modules pass.

**A rebuild stopped by hand leaves the instance's status alone (6-nov-2026).** Until its restart step the instance runs its last build: the build and the boot test touch no live container, and the failure's `status: error` said something untrue of a working instance. `RebuildInstanceExecutor.on_cancelled_running` writes the steps that ran to the log and asks for a state-only probe (`_refresh_state_now`; `cloud.job` asks for none after a cancellation). What the stop leaves on the host is said in the log (`_warn_unapplied`, also from `on_abort`, for a rebuild whose worker died). Before «Rebuild Odoo image» the host already holds what «Update with copier» and the steps after it rewrite in place — the compose files and their link, the stripped services and capped hostnames, `backup.env` and the other env files, `docker-compose.override.yml`, `addons.yaml` and `repos.yaml`, `incubacloud_connect`, the Odoo conf, `pip.txt` and `apt.txt`, uncommitted until the next rebuild's «Commit dirty files» — and once the build finished, the image's tag points at an image neither boot-tested nor applied to the database's modules. The containers still run the previous build, but anything that recreates them (`docker compose up`: a Start, a restore, a move, a deploy) would use those files and that image; `restart` does not recreate. Stopped between «Update with copier» and «Restart instance», the log warns of it — saying whether the image may have been rebuilt — and says to rebuild first. The steps are read from the job log, which keeps every attempt's «Running:» lines, so a stop handed no results is told the same. Decided: a warning, no block. A rebuild that fails at the same point (its build, its boot test) leaves the same and has always left it, with `status: error` and no block; a block worth its name covers both, and every way a job ends, so it belongs on the host — a marker the rebuild lays before copier and lifts after its restart, which `compose_op.sh up` refuses — and is proposed apart. `last_rebuild_fingerprint` is only written by a success, so the next rebuild is a full one when the configuration changed. A restore, a `backup_restore` and a cutover still end in error when stopped: the database may be half restored, or the source frozen.

**The build follows the branches, not the cache (5-nov-2026).** The build is full (`--pull --no-cache`) only when `rebuild_fingerprint` changed; otherwise it is `docker compose build odoo`, with Docker's cache. Doodba clones every repository *inside* the image (its ONBUILD `gitaggregate`, right after `COPY ./custom`), so whether that clone runs again depends only on the build context. The only thing in it that changed between two pushes used to be the GitHub token in `repos.yaml`, which rotates every hour: a second push within the same hour was rebuilt in a minute, every layer `CACHED`, the boot test and `click-odoo-update` found nothing to update, and the panel showed the push as deployed while the old code ran (production, 5-nov-2026). Now, before the image is built, `deploy.sh record-heads` writes `odoo/custom/incubacloud-heads.txt` (`<alias> <ref> <commit>` per repository, odoo included) into the context: a branch that moved changes it and the clone runs again. This is about correctness, not speed: it promises no cache hit. The token in `repos.yaml` still changes every hour and odoo/odoo's series branch moves several times a day, so in practice the clone layer is rarely reused, and a rebuild that does reuse it is one within the same hour with no repository moved. The heads are asked with `git ls-remote` for the exact `refs/heads/<ref>` and `refs/tags/<ref>` (a bare pattern also matched `refs/heads/x/main` or `refs/pull/*/head`; both kept when both exist, since a fetch prefers the tag; a full `refs/...` ref is asked as it is), with the same URLs and token as `repos.yaml`, rendered once and read back from it (`_repo_heads_spec`), staged owner-only as `repo-heads.tsv` in the job's directory. git runs with a `HOME` of its own and `GIT_CONFIG_NOSYSTEM=1`, `credential.helper=` and no prompts, so a credential helper of the host's SSH user (store, cache, libsecret, a credential manager) is never handed the token, which it would otherwise keep (`~/.git-credentials`); variables rather than `GIT_CONFIG_GLOBAL`, which git before 2.32 ignores. An https URL's credentials go as an `Authorization` header in that HOME's config, not on git's command line, which every user of the host can read in `ps`; the build's own clone inside the container still carries them in its URL, as before. Neither the token nor git's own messages reach the log or the file. Each lookup has 20 s (`protocol.version=2`); once one runs out, the rest are not asked and count as unreadable. A pinned repository is its own head and is not asked; whether it is pinned comes from where its ref came from (`odoo_commit_sha`, `commit_sha`, or a layer's `_repo_merge_ref` answering a commit, such as a release pointer), passed as `pin`/`ref` in the spec, never from its shape: `cafebabe` or `20261105` is also a branch name. A head that cannot be read (GitHub out of reach, a branch the remote does not have, a lookup that timed out) is never taken as unchanged: it gets a value of its own, which rebuilds the repositories without cache, and a warning in the log; if GitHub really is out of reach, that clone fails the build instead of shipping old code. The file is in `odoo/custom/`, which the template's `.dockerignore` (v10.0.8: `custom/src/*` but its dotted files, `auto`) does not leave out, and is kept out of the instance's git history. The rebuild runs it in its «Rebuild Odoo image» step, so a layer that leaves the build out leaves the lookup out with it; the deploy, whose image is built by its «Build Odoo image» step, runs it as «Record repository heads» after «Write repos.yaml», which covers a deploy run again over the same context.

**The repositories are downloaded on the host, not in the build (10-nov-2026).** Every series (`prefetch_repos` on its card: all but 19.0 from core 1.0.222, 19.0 too from 1.0.224) downloads each repository of `repos.yaml` on the host before the image is built, in the step «Fetch the repositories» (`deploy.sh fetch-repos`), and builds with `AGGREGATE=false`: doodba's `100-repos-aggregate` then does nothing and the rest of the build is unchanged. The credential of a private repository never enters the image, its build context, its layers, Docker's build cache or record, or the instance's container; `repos.yaml` on the host has none (`_strip_repo_credentials`), and the URLs with their credentials travel only in the staged spec, `repo-heads.tsv`, which `fetch-repos` removes when it ends, however it ends. The steps «Record repository heads» and «Trust the Git servers» are those of a series the parameter below sends back to cloning in the image.

- *How.* One helper image for every series, doodba's 19.0 by digest (`GIT_HELPER_IMAGE`: git 2.39.5, git-aggregator 4.0), because the git that handles a credential has to be a maintained one and 8.0 to 15.0's images carry old ones. The host keeps it under a local tag, `incubacloud-git-helper:<12 hex of its digest>`, built from it with the label the daily prune spares, so it is not downloaded again every day; a full setup prepares it, and the daily maintenance does on a host with an instance of a series that fetches (`ic_git_helper_image`), so no job pays its 730 MB; a job that has to pull it has 300 s for it. The tags of other digests are removed as soon as the current one is there: the label would keep each for ever. The container runs as the host's user with `--cap-drop ALL`, `no-new-privileges` and a cap on its processes. Each repository is downloaded by the command doodba's `autoaggregate` runs, `gitaggregate --expand-env --config repos.yaml -d <alias> aggregate`, from a copy of the instance's `repos.yaml`, with the series in `ODOO_VERSION`, `umask 0027` and the container running as the host's user. The credential goes as an `Authorization` header scoped to that repository's URL in an owner-only HOME mounted read-only, one per repository, removed when the container ends; redirects are refused for every server; a GitLab server keeps its own CA and pinned address. A `repos.yaml` entry with a key core does not render (`shell_command_after` and the like, which git-aggregator would run where the credential is) refuses the job. Several merges are supported. The tree loses its `.git`; the image then has none, Odoo's included (206 MB on 19.0); nothing in Odoo, doodba or core reads it, and `incubacloud-heads.txt` still says, inside the image, which commit each repository is at.
- *Only what moved.* Each tree has a marker, `odoo/custom/src/.ic-heads/<alias>`: its commit, or with several merges the SHA-256 of their `<ref> <commit>` lines. The heads are read first, as before; a tree whose marker matches is left alone. A head that moved between the reading and the download is accepted, and the commit that arrived is named in the marker and in `incubacloud-heads.txt`; a pinned commit has to arrive or the step fails. With several merges the container tells only the commit of their merge, so after the download their heads are read again (`ic_heads_unmoved`): if one moved, or cannot be read, the tree is kept under a key of its own and a marker that matches no heads, so no other instance takes it and the next run fetches it again (10-nov-2026). A head that cannot be read is never taken as unchanged.
- *One tree per commit on each host.* The downloaded trees are kept in `~/.incubacloud/git-trees/<key>/tree`, the key being the SHA-256 of the merges' URLs (without credentials) and commits, and each instance's `odoo/custom/src/<alias>` is a copy of it made of hard links (`cp -alT`; a plain copy, which the log warns of, on another file system), put in place through a temporary tree: the old tree is renamed aside, the new one takes its name and the old one is removed last, so a cut run never leaves the instance without a tree for long. A lock per instance (`odoo/custom/src/.ic-fetch.lock`) keeps two downloads of it from linking at once; a new job stops the run an earlier one left. A job holds the cache's lock (`git-trees/.lock`) shared while it checks, links or stores a tree, and the daily maintenance takes it exclusive without waiting, or leaves the trees for the next night; it also removes an entry left without its `head`. A tree is taken from the cache only when this instance's credential reads the repository now: a branch's head is read with it in the same run, and a pinned commit's repository is asked with it (`ls-remote`) first, so a repository taken away from the App or a rotated token stops the next deploy. The instance's marker is a hard link to the cached tree's `head`, so its link count says how many instances use it: the daily maintenance removes the trees whose `head` has no other link and has not changed for two hours. A host serving 25 panels at the same commit of Odoo holds one tree of it (1.2 GB on 19.0) instead of 25. BuildKit sends a hard-linked file as an ordinary one, its layer cache is the same, and doodba's `800-permissions` changes only the image's copy (checked 10-nov-2026). The trees are never written in place: such a write would reach every instance linking them. The host's account deploys for one panel only, which is what lets its instances share the trees.
- *Time.* The step has a fixed budget of 1 200 s (`_FETCH_BUDGET_S`), whatever the number of repositories, with 600 s for each and one retry, 60 s later, only when the first attempt did not run out of time and time is left; the step's timeout is a minute more. `deploy.sh` keeps the budget itself and its traps remove the container, the HOME and the temporary trees on a cancel; after a SIGKILL the next run on the instance removes them. It writes the seconds it took to `odoo/custom/src/.ic-fetch-seconds`, which the build's repetition adds to its first attempt (below). In a rebuild the step runs inside the host's build lock, as the clone did inside the build.
- *Build context.* `odoo/Dockerfile.dockerignore` is the template's `.dockerignore` with `!custom/src/<alias>` for each repository and `custom/src/.ic-*` last. The trees, the markers and that file are kept out of the instance's history, and out of an export, whose `repos.yaml` keeps every line without credentials. What cloning in the image needed (`build.d/060-incubacloud-git`, `odoo/custom/incubacloud-git/`) is removed. Docker keeps the context of each build, the trees included, in its build cache: the build step of a deploy and of a rebuild ends by removing the contexts no build is using (`build_context_prune`, `docker builder prune -af --filter type=source.local`), whatever the build did and without changing its status, so a night that rebuilds many instances does not hold one copy of the trees for each until the daily prune; the layers, cached by content, stay (10-nov-2026).
- *The way back.* The system parameter `incubacloud.repos_in_image_series` (series separated by commas, empty by default) sends a series back to cloning in the image without a new version of core, except 8.0 to 10.0, whose git 2.1.4 sends a token in clear after a redirect (`image_git_safe`). The next deploy or rebuild of each instance of it removes its trees, markers and ignore file (`record-heads`) before the image clones again. See [RB-32](runbooks/RB-32-git-repositories-on-the-host.md).

**What a host is handed from GitHub (10-nov-2026).** For each GitHub line the panel asks `GET /repos/{owner}/{repo}` with the App's installation token, then with the personal access token, and takes the repository's `id` and `private` from the answer: per repository, never per owner. A private repository the App reads gets a token of the App limited to the instance's private repositories the App reads, with `contents: read` and `metadata: read` (`GitHubAppClient.get_scoped_installation_token`), asked once per job and never cached; one only the PAT reads gets the PAT; a public one gets nothing, whoever reads it; one neither reads gets nothing either, and the job's log names it. Only a 404, or a 401 or 403 that is not a rate limit, means a token does not read it; a timeout, a 5xx, a rate limit or an answer without an id is asked again once and then refuses the job with the reason, rather than fetching without credentials (or handing the PAT where the App reads it). The installation's own token, which serves the panel's calls to GitHub's API, never leaves the panel. A series sent back to cloning in the image gets the same credentials in its `repos.yaml`. The PAT stands in for the App only where it does not stay in the image. When GitHub refuses the installation's token (a 4xx) or fails to issue it twice, the job goes on without it and its log says which: the PAT alone is asked who reads each repository, so an instance whose repositories are public deploys anyway; a private one the PAT reads gets the PAT on a series that downloads on the server (`_prefetches`), naming it in the log, and refuses the job on a series that clones into the image, since the App might read it and the PAT would stay in the image. When GitHub refuses the scoped token, a series that clones into the image is refused; one that downloads on the server asks the PAT alone about those repositories and hands it to them, naming each in the log, if it reads every one, or refuses the job naming those it does not read.

**A failed build is tried once more (31-oct and 8-nov-2026).** The build clones every repository, so a passing failure at GitHub (`curl 55`, a broken pipe in `100-repos-aggregate`) failed the whole job. «Rebuild Odoo image» and the deploy's «Build Odoo image» (`docker compose build odoo`, cached and without a pull, between «Pull images» and «Start database», `stop_on_failure`) run it through `_build_retried_once`: a failed build waits 60 s and runs again, from the layer that failed when the cache kept the others. Before 8-nov-2026 the deploy had no build step: the first `docker compose run` or `up` that found the image missing built it, never twice. A first attempt that ran 900 s or more is not repeated (`_BUILD_RETRY_MAX_FIRST_S`, timed with bash's `SECONDS`): the job runner kills a job at 3600 s, and that kill leaves the job orphaned and the instance in `deploying`. Where the repositories were downloaded before the build, the seconds «Fetch the repositories» took count with the first attempt's (`.ic-fetch-seconds`, 10-nov-2026), so the worst case of the job does not grow with the download. A move's deploy, and the deploys a layer builds on this one, keep the step.

## Instance logs: the compose override and the daily archive

Besides the copier-rendered `prod.yaml`/`test.yaml`, every deploy and rebuild writes a `docker-compose.override.yml` next to them (`DeployInstanceExecutor._resource_override_content`, extended by a layer's executors through `super()`). Compose loads it automatically because every `docker compose` call the executors run uses default file discovery — never `-f prod.yaml`, which would skip it. Per service it carries the resource limits configured on the instance, the `incubacloud.protect=1` label that keeps the daily `docker_prune` away from panel-managed stacks, and a `logging:` block (`json-file`, `max-size`/`max-file` from `cloud.settings`, `10m` × 3 by default).

That cap exists because a container's log otherwise grows until the disk is full: doodba's Odoo logs to stdout, the template sets no logging driver, and only a host that ran `host_hardening` has a `daemon.json` saying otherwise — a Base-mode host set up by `full_setup` alone has none, and daemon defaults only apply to containers created afterwards.

### Odoo's own log is a file on the host

A capped container log is still the wrong place to keep history: it lives inside the container, and a rebuild recreates the container by design, so yesterday's log goes with it. The `odoo` service therefore gets two more keys in the override:

- `command`: the environment's own command plus `--logfile=/var/log/odoo/odoo.log`;
- `volumes`: `./logs:/var/log/odoo`, a bind mount of the instance's own directory.

The flag rides on the command rather than on `odoo.conf` deliberately. The panel runs one-shot containers whose output has to keep reaching the job log — `docker compose run --rm odoo odoo -i <module>` and `click-odoo-update` for the boot test — and `run` replaces the command, so they are unaffected by construction; a `logfile` in the conf would have redirected them into the instance's log file, including tooling with no flag to opt out. The cost is that the override replaces the command outright, so whatever each environment's compose file put there has to be repeated: `prod.yaml` sets none (the image's `CMD`, `/usr/local/bin/odoo`), `test.yaml` pins `--workers=3 --max-cron-threads=1`. Both are asserted by tests and are worth re-checking when the copier template pin moves (RB-15).

`logs/` is created and chowned to uid 1000 before the stack starts (`scripts/instance_logs.sh install`, run by deploy and rebuild): Docker creates a missing bind-mount source itself, as root, and Odoo would then be unable to write and fall back to stdout.

### Rotation and retention

The same script writes `/etc/logrotate.d/incubacloud-<compose project>` on the host: `daily`, `dateext`, `compress`, `delaycompress`, `nocreate`, `rotate <cloud.settings.odoo_log_archive_days>` (60 by default). The host's own daily logrotate run does the work — no panel job is involved, so the archive keeps advancing even while the panel is down. `nocreate` matters: a file logrotate created would belong to root and the container could not write to it; Odoo recreates it on its next line through `WatchedFileHandler`, which also means rotation needs no signal, no restart and loses no lines. `delete_instance` drops the config, and the logs go with the instance directory.

The result on the host mirrors what a comparable hosting platform shows: `odoo.log` (today), `odoo.log.<yesterday>` (plain), `odoo.log.<older>.gz`.

### Reading it back

- Live view: `tail -n N logs/odoo.log`, falling back to `docker compose logs` for an instance not rebuilt since this shipped.
- Archive: `/cloud/instance_log_archives` lists what the host keeps, `/cloud/fetch_log_archive` reads one (with an optional fixed-string filter applied on the host), `/cloud/search_log_archives` answers *which* days mention a term, and `/cloud/instance/<id>/log_archive/<name>` downloads a day gzipped. All gated by `can_view_logs`; the file name is validated against the shapes logrotate produces before it reaches a shell.
- The viewer's day picker filters as you type (sixty days do not fit a dropdown) and steps day by day; pressing Enter in the filter box sweeps every archived day on the host and marks the ones that match with their hit counts. The sweep is bounded by a timeout and emits a completion marker, so a run cut short reports itself instead of reading as "no matches".
- Cost and accountability: the read endpoints share one per-user cap (`rate_limit_logs_per_min`, 60/min — the live tail polls every 4 s, so a lower cap breaks a single open viewer), counted in a bucket per endpoint family (`logs_tail_`, `logs_list_`, `logs_day_`, see RB-04 for why one shared bucket was a serialization failure on every viewer open), and the sweep and the download share a tighter cap (`rate_limit_log_search_per_min`, 6/min). What each read may cost the customer's host is configurable rather than baked in: `log_download_max_mb`, `log_search_max_files` and `log_search_timeout_s`, all on Settings → General → Instance Logs. Opening the viewer, searching every day (with its term) and downloading a day write a `cloud.audit.log` row; polling the live tail deliberately does not, or one row every four seconds would bury the ones that answer "who read this instance's logs".
- Security of those reads: the endpoints are gated by `can_view_logs` (Developer+) and read the instance through the caller's own environment, so record rules decide which instances are visible. The file name is matched against the exact shapes logrotate produces before it reaches a shell, the search term is passed as a quoted argument, and **every command refuses anything that is not a regular file**. That last one is not cosmetic: `logs/` belongs to the container's uid, the panel's terminal is deliberately confined to the container, and the reader runs on the host as the SSH user — so following a symlink planted from inside the container would turn the log viewer into a host file reader. The listing only offers regular files, and the read, download and sweep each check `[ -f … ] && [ ! -L … ]`. The sweep's `log_search_max_files` budget is spent on real log files only — candidates come from `find -type f` restricted to logrotate's exact shapes, ordered by mtime — so a planted link or a junk `odoo.log.*` cannot push the real days out of it. A plain day that was compressed after it was listed is read (and downloaded) from its `.gz` twin, so a viewer left open over midnight keeps working. All of these commands are exercised for real by `tests/test_instance_log_commands.py`, which runs them through `sh` against a temporary `logs/` with real files and a planted link.
- The health probe scrapes ERROR lines from the file, filtered by timestamp with an awk state machine that keeps each traceback attached to its header, reading the newest archive alongside the live file so the once-a-day midnight rotation does not open a hole. It reads regular files only too: the newest archive comes from `find -type f`, and `tail`/`stat` on `logs/odoo.log` run only when it is not a link — the probe runs on the host as the SSH user, and a link planted in `logs/` would otherwise carry host-file lines into an alert. It also grades the archive itself and raises `instance_logs_unhealthy` when Odoo is logging to the container instead of the file, or when the live file grew past 512 MB (nothing is rotating it).
- The probe's own job log is held until the check ends. A cycle that passed and reported nothing through an alert, not even a first suspicion, keeps only its verdict line: its readings are on the instance already. Any other cycle keeps every line. Every five minutes for every instance, full logs of checks that found nothing were 83% of the panel's job log rows.

### The proxy's access log

Traefik writes one JSON line per request to `/var/log/traefik/access.log` on the host (mounted into the proxy at the same path). Full Setup installs its rotation (`scripts/proxy_access_log.sh`): daily, or past 100 MB — looked at every ten minutes by a timer of its own (`incubacloud-traefik-logrotate.timer`), because the distro's daily run alone would let a flooded host fill its disk between two runs — compressed, removed after 30 days by age so a busy host rotating several times a day still keeps the full month; the proxy is sent `USR1` to reopen the file, so no line is lost. It used to go to stdout, where Docker kept 30 MB in all and the path changed with every recreate of the container. The panel's "Recent requests" reads the file, together with the end of the previous one so the page is not empty right after the nightly rotation (falling back to `docker logs` on a host not set up since), the log collector ships it, and the host's web-login jail watches it.

## Memory an instance is deployed with

Besides the containers' `mem_limit`, every deploy and rebuild sizes the memory settings of Odoo and PostgreSQL from the instance's own limits (`odoo_memory_limit` and `db_memory_limit`, the **Resources** tab). Nothing is stored: the values are computed when `odoo.conf` and `docker-compose.override.yml` are rendered (`DeployInstanceExecutor._conf_content` and `_resource_override_content`), so the instance's fields and its saved configuration stay as the user wrote them.

| Setting | Written to | Formula | Bounds |
|---|---|---|---|
| `limit_memory_soft` | `odoo.conf`, `[options]` | 60 % of the Odoo limit | at least 640 MiB, at most 2048 MiB |
| `limit_memory_hard` | `odoo.conf`, `[options]` | 150 % of the Odoo limit | at least 1536 MiB, at most 2560 MiB |
| `shared_buffers` | `CONF_EXTRA` of `db` in the override | 1/4 of the database limit | at least 16 MB |
| `work_mem` | same | 1/16 | at least 4 MB, at most 64 MB |
| `effective_cache_size` | same | 1/2 | at least 32 MB |

The constants are `_ODOO_MEMORY_SHARES` and `_PG_MEMORY_SHARES` in `models/deploy_instance_executor.py`, and `tests/test_instance_memory_settings.py` pins every size below.

| Odoo limit | soft | hard | | Database limit | shared_buffers | work_mem | effective_cache_size |
|---|---:|---:|---|---|---:|---:|---:|
| 640m | 640 MiB | 1536 MiB | | 192m | 48MB | 12MB | 96MB |
| 1024m | 640 MiB | 1536 MiB | | 256m | 64MB | 16MB | 128MB |
| 1280m | 768 MiB | 1920 MiB | | 512m | 128MB | 32MB | 256MB |
| 2g (core's default) | 1228 MiB | 2560 MiB | | 1g (core's default) | 256MB | 64MB | 512MB |
| 4g and above | 2048 MiB | 2560 MiB | | 4g | 1024MB | 64MB | 2048MB |

An instance without a limit gets none of this: Odoo keeps its own defaults and PostgreSQL the template's settings.

The Odoo limits are written only when Odoo runs workers: the `--workers` of the service's command (staging's pins 3) or, failing that, `workers` in the configuration (`_odoo_runs_workers`). In threaded mode (`workers = 0` or none) `limit_memory_soft` is checked against the virtual size of the whole server, which is past 640 MiB from the start, and Odoo reloads itself every time it is (`ThreadedServer.process_limit`): a reload loop. And `limit_memory_hard` would be an `RLIMIT_AS` on that whole process. Such an instance keeps Odoo's defaults; on 5-Nov-2026 every instance in production had workers (review of that day).

### Where the numbers come from

Measured on 5-Nov-2026 on production panels whose Odoo had 896 MiB, three HTTP workers and a cron worker, with `/proc` inside the container and the cgroup's `memory.stat`:

- **Per process (PSS):** prefork master 82 MB, HTTP workers 112-152 MB after days of use (88 MB 34 hours after a start), gevent 132 MB, queue_job's jobrunner 102 MB, cron worker 79 MB. The fixed part (master, gevent, jobrunner) is 260-320 MiB; each HTTP or cron worker costs about 85 MiB when it starts and 110-150 MiB after days. The memory was real, not cache: 767 MB anonymous, 38 MB of file cache.
- **Nothing recycled a worker.** The panel set no `limit_memory_*`, so Odoo's defaults applied: 2 GiB soft and 2.5 GiB hard per worker, in a container of 896 MiB. No worker was ever recycled for memory. Python does not give memory back, so each worker grew in steps, mostly during the nightly jobs (02-04 UTC), until a deploy restarted the container: one panel went from 540 to 780 MiB in ten days and settled at 87-92 % of its limit. The only ceiling was the container's, and a peak on that plateau ends in the kernel killing a worker.
- **`limit_memory_soft` is checked against a worker's virtual size**, not its resident memory (`memory_info` in `odoo/service/server.py` returns VMS on Linux). Workers days old sat at 480-500 MB of VMS, so the soft limit never goes below 640 MiB: about 140 MB of margin, enough to recycle the workers that keep growing without recycling one on every request. Past it, a worker finishes its request and is replaced.
- **`limit_memory_hard` is an `RLIMIT_AS`** set on each worker and inherited by what it starts, wkhtmltopdf among them. Below 1.5 GiB of address space a PDF report fails, so the hard limit never goes lower; the container's limit is the real hard limit, and this one only stops a runaway worker in a large container.
- **The ceilings are Odoo's own defaults:** the panel tightens the limits, it never loosens them.
- **PostgreSQL ran the template's `work_mem = 512MB`** (doodba-copier-template's `CONF_EXTRA`), with `shared_buffers` at 128MB and `effective_cache_size` at 4GB, whatever the container. One sort may take 512 MB and one hash 1 GiB (`hash_mem_multiplier` is 2), more than most databases the panel deploys are given (1g by default): the kernel kills that backend and PostgreSQL restarts every connection. A database of 256 MiB used 130-135 MB of its own memory; the rest of its usage was page cache. The fractions are those the manager's own database was given on 27-Oct-2026 (1 GiB, `work_mem = 64MB`), and so is the ceiling of `work_mem` (review of 5-Nov-2026): it is per sort or hash of each connection, so on a large database with many connections a sixteenth would multiply past the container's limit, while `shared_buffers` and `effective_cache_size` are one per server.
- **Out-of-memory kills went unseen.** cAdvisor's `container_oom_events_total` counted kills in the panels' `smtp` containers (36 in a month on one of them) and no alert said so.

### Alerts

- **`instance_high_memory`** (the SSH health probe, every 5 minutes): 95 % of the container's limit for six checks in a row, 30 minutes (`_MEM_WARN_PCT` and `_MEM_STREAK_REQUIRED` in `models/instance_health_executor.py`). It was 85 % for two checks, with the streak shared with the CPU: with no ceiling on the workers, any instance awake for a few days sat on its plateau and kept it open with nothing wrong. The CPU keeps 90 % for two checks.
- **`metrics_instance_oom`** (a metric rule, `data/metric_rule_data.xml`, critical): any process killed for lack of memory in the `odoo`, `db` or `smtp` container of an instance in the last 15 minutes. A kill is the fact that matters. The database has no alert by percentage: its usage is mostly cache and always reads 90-95 %. It counts with `increase_prometheus`, not `increase` (review of 5-Nov-2026): VictoriaMetrics' `increase` takes a series that appears inside the window, or comes back after a gap in its samples, as starting from 0, so a counter that already read 2 raised two kills that happened earlier (checked on v1.102.0, the central's version). `increase_prometheus` reads only the samples inside the window; it still sees a kill after a counter reset, and misses one only before a series has two samples.
- **`instance_memory_recycling`** (the SSH health probe, warning): more than 12 workers recycled for memory in the last hour (`_RECYCLE_WARN_PER_HOUR`, `_RECYCLE_WINDOW_MIN`), counted from Odoo's INFO line `Worker (…) virtual memory limit (…) reached` in `logs/odoo.log` (`_memory_recycles_command`). Added after the review of 5-Nov-2026, because the 640 MiB floor recycles in silence: a few a day are the limit doing its job, one every five minutes means the workers cross it as soon as they warm up, the floor is too low for that instance's work and each request after a recycle starts on a cold worker. It leaves the instance's status alone (the instance works) and closes when the hour holds 12 or fewer. The remedy is a larger Odoo limit, or `limit_memory_soft` in the instance's configuration.

### Changing them

- **When they apply.** On the instance's next deploy or rebuild; saving the instance changes nothing on the host and does not mark its configuration as changed, since the values derive from fields already in the snapshot. A new `odoo.conf` restarts Odoo. A new `CONF_EXTRA` recreates the `db` container: the database restarts (seconds) and Odoo reconnects.
- **Raising or lowering the Odoo limit** moves both per-process limits within their bounds. Below about 1 GiB the floors apply, and the container's limit is the one that bites first. With workers, the prefork master is never limited, only its workers; a one-shot `odoo … --stop-after-init` run reads the same `odoo.conf` without the service's command, so on a staging whose configuration has no `workers` it runs threaded under the hard limit (1.5 GiB of address space at the floor).
- **Overriding Odoo's.** Write `limit_memory_soft` or `limit_memory_hard` (bytes; `0` turns a limit off) in the instance's configuration (**Config** tab, `odoo_conf`). If either is there, the panel adds neither, so a hard limit of the panel's never sits under a soft one of the user's. A layer on top may set its own after core's, which win.
- **Overriding PostgreSQL's.** `ALTER SYSTEM SET work_mem = '128MB'` (and `SELECT pg_reload_conf()`, or a restart for `shared_buffers`) inside the instance's database: `postgresql.auto.conf` lives in the data volume, survives rebuilds and wins over `postgresql.conf`, where `CONF_EXTRA` lands. `ALTER SYSTEM RESET work_mem` goes back to the panel's value. It does not survive a move to another host, nor a restore into another instance: both load a dump (`backup_download` and `restore`), which carries the database and not the server's `postgresql.auto.conf`, so the panel's values apply there until it is set again (review of 5-Nov-2026). An addon's override fragment cannot replace `CONF_EXTRA`: fragments never overwrite what the platform rendered.
- **Changing a formula** is a change of the constants above and of their tests. It reaches every instance on its next rebuild, which restarts its database too.

## CPUs an instance is deployed with

Each service's `cpus` in `docker-compose.override.yml` is `min(field, NCPU)`: the instance's `odoo_cpus`, `db_cpus`, `backup_cpus` or `smtp_cpus`, at most the host's CPUs as its Docker daemon counts them. Docker refuses to create a container whose `cpus` is above that count ("range of CPUs is from 0.01 to 2.00, as there are only 2 CPUs available"), and by then `docker compose up -d` has recreated `db`: on 8-Nov-2026 (job 457397) a limit of 2.5 CPUs applied on a server of 2 left the database `Created`, never started, and the panel down. Every deploy and rebuild renders the override in `DeployInstanceExecutor._resource_override_content`, so the limit holds on all of them, a move's deploy on its target included.

- **Source.** `docker info --format '{{.NCPU}}'`, asked by `_read_host_cpus` when the job uploads its files, with a timeout of `HOST_CPUS_TIMEOUT_S` (15 s). It is the number Docker checks against, read at that moment. A daemon that fails, does not answer in time or answers no positive count falls back to the host's `cpu_cores` (the metrics', up to five minutes late after a resize, 0 on a host never measured); with 0 too, nothing is limited and the job's log says so.
- **Margin 0.** Docker accepts `cpus` equal to the count: 2.0 on a server of 2 runs (job 457396). A margin would lower limits that fit today and avoid no failure.
- **What is limited is what the host is given.** The fields keep their value, so the host's accounting and placement count what was set, the configuration's hash does not depend on the host (no false drift, no "changes to apply"), and a move to a larger host gets the full value again. `cpus` is a CFS ceiling, not a reservation: a container cannot use more CPUs than the host has, so the limit takes nothing a service could have used. Each limit is a line in the job's log, and the end hooks hand what was limited to `_report_cpu_clamps`, which a layer extends to tell its operator.
- **A host that shrinks.** A server resized down keeps its stacks' overrides until each is rendered again. A start, restart or restore that is no rebuild reuses the override on the host, so Docker may refuse the containers of a stack whose `cpus` is now above the count, as it refused job 457397's. A rebuild of each instance renders the override for the smaller server; after a resize down, rebuild its instances. A server that grows keeps the limited values until the next deploy or rebuild of each instance, as the hash does not mark them.

`tests/test_deploy_override_cpus.py` pins the limit, the fallback and the timeout.

## Odoo series: one card each

`models/_odoo_versions.py` is the one place an Odoo series is described, and nothing else in the panel decides on a version by itself. Each series has a card: whether it is `offered` (in the pickers and accepted by the importer), the PostgreSQL range and default (`postgres`), the tool that dumps and loads its database (`db_tool`) and the lowest doodba template able to render it (`template_min`). A series being prepared lands with `offered=False`, so the code that supports it ships before a customer can deploy it; a series that needs something new gets a field on the card, not an `if version` somewhere.

The panel knows Odoo 8.0 to 20.0 and offers 18.0 to 20.0; each older series opens when its run of the series passes (`offered` in `_odoo_versions.py`), and runs with every service of the panel or is not offered (7-nov-2026): 7.0 is retired, since its click-odoo can neither dump, restore nor update its database. Each runs on the PostgreSQL range and tool of its card, the range Odoo and doodba's template recommend unless a reason dated beside the card says otherwise: 16.0 to 19.0 on PostgreSQL 14 to 18 with `click-odoo`, and 20.0 (offered since 1.0.198) on PostgreSQL 16 to 18 with `odoo-db` and doodba template v10.0.3 or newer. No series runs below PostgreSQL 12, the first that continuous recovery serves, which 9.6 lacks as well as a backup service (7-nov-2026): 8.0 to 10.0, for which the template allows 9.6 alone, run on 12 alone, 11.0 and 12.0 on 12 to 13, with 13 by default, and 13.0 to 15.0 on 12 up to 16 (13.0 and 14.0) or 17 (15.0), inside the template's range, which starts at 10. Copier refuses a PostgreSQL outside the template's `pg_per_odoo`, a question the template never asks and keeps out of `.copier-answers.yml`: given as an answer, it would reach `copier copy` but not the replay of the last render that `copier update` starts with. So the deploy and the rebuild of a card with `postgres_beyond_template` write a copier settings file whose defaults hold the card's range (`copier_defaults`), and `ic_copier` points copier at it (`IC_COPIER_SETTINGS`); every other series runs copier as before. The image of 8.0 to 10.0, on Debian 8, reads apt from Freexian's Extended LTS of jessie, whose keyring the build checks against a fixed sha256 (`debian_archive`, `scripts/doodba/debian_archive.sh`), so the packages of an `apt.txt` install with their signatures checked. On 8.0 a session opened by Connect as user holds a signed password of its own, which `incubacloud_connect` accepts in `res.users.check_credentials`: 8.0 has no session token and checks the session's password on every call.

A panel offers a series only if its pinned template (Settings → Doodba template version, `copier_template_ref`) can render it (`template_ref_allows`; an empty pin is the template's default branch, newer than any tag): the pickers, `may_choose` and the default all read `offered_versions(pin)`. The default of `cloud.project` and `cloud.instance` is the newest of those (`default_version`; 20.0 under production's v10.0.8, 19.0 under a pin below v10.0.3), read when a record is created: the rows that exist keep their series. A new instance runs its project's series unless it names one (`cloud.instance.create`, whoever creates it: the panel's form, an import from a host, code); only an instance without a project takes the default. A layer that creates instances of its own may name their series. An administrator may still choose a series the pin cannot render, and its deploy refuses with RB-15; anyone else reads that it is not offered on this panel. A save that sends back the series a record holds is no choice: `write` drops it (`without_unchanged_series`), so a pin rolled back below a series' floor does not lock the records of that series. The 1.0.198 migration raises a stored pin that is a version tag below v10.0.3 to v10.0.8, both tags written in the migration itself.

What reads the card:

- `cloud.instance` refuses a PostgreSQL outside the series' range when saved, and `/cloud/get_odoo_versions` hands the SPA the cards so the PostgreSQL picker offers only that range (`static/src/utils/odoo_versions.js`).
- The deploy and the rebuild ask `cloud.instance._check_template_ref()` before uploading anything: a pin older than the series needs fails with the runbook's name (RB-15) instead of inside copier.
- The operation scripts never name a database tool. The executor passes the series' tool in the script's environment (`run_script(..., env=script_env(inst.odoo_version))` → `IC_DB_TOOL`), and `scripts/lib/common.sh` turns an operation into that tool's argv (`ic_db_dump_args`, `ic_db_load_args`, in `IC_DB_ARGS`). `click-odoo` is click-odoo-contrib's `backupdb`/`restoredb`, every series up to 19; `odoo-db` is `odoo db dump`/`odoo db load`, Odoo 18 and later and the only one on 20, where click-odoo-contrib 1.24 refuses its database commands. Every dump and load of an instance — the live backup, the download, the neutralized copy, the restore, the export's instructions, a layer's own backups — goes through those two functions, so a third tool is one more case there and a value on a card.

## Dependency re-sync and provenance

An unpinned repo line is aggregated at its branch tip, so a rebuild ships whatever upstream published since the last one. Deploy and rebuild therefore re-read the `requirements.txt` of every repo **without** a `commit_sha` just before writing `pip.txt` (`DeployInstanceExecutor._resync_repo_requirements`, inherited by every rebuild variant, a layer's included). Pinned repos are skipped: frozen code, frozen dependencies. A fetch that fails is logged and ignored — the stored list is used rather than stopping the fleet on a GitHub blip.

Merging upstream on every rebuild only works because each package remembers who wrote it. `pip_dependency_sources` (a JSON map on `cloud.project` and `cloud.instance`, provided by the `cloud.pip.provenance.mixin`) maps `package → {repo, spec, label, rejected?}` and holds repo-owned packages and the answers to resolved conflicts — no entry, or an empty `repo`, means the operator owns the line. The merge then decides per package:

| Situation | Outcome |
|---|---|
| Package absent | Added, owned by the repo |
| Same spec, unowned | Ownership claimed (lazy backfill — no migration) |
| Different spec, owned by this repo | Applied in place, logged in the job |
| Different spec the stored line already meets (`pip_spec_relation`) | Skipped, logged («already met») |
| Stricter spec that meets a bare name | Replaces it, owned by this repo |
| Spec turned down when a conflict on the package was resolved (`rejected`) | Skipped, logged («turned down») |
| Any other different spec (including a stricter pin against a version or range the operator or another repo wrote) | Conflict marker + `pip_conflict` alert, job fails |
| Package dropped upstream | Never removed — noted in the job log |

Ownership is keyed by repo URL, not branch, so switching branches does not hand a package back to the operator. Writing `pip_dependencies` outside the managed paths prunes the entries whose spec no longer appears verbatim (the edit makes those lines the operator's); the managed paths — the requirements merge and `/cloud/resolve_pip_conflict` — pass `pip_provenance_managed` in the context and set the map themselves. Resolving a conflict in favour of the repo's spec hands the line back to it; keeping the stored spec keeps its owner (operator-owned when it had none); a third spec makes it operator-owned (an entry with an empty `repo`). The side not chosen goes to the entry's `rejected`, which the re-sync skips; removing the markers by hand and leaving one side, once and with no piece of a marker left, records the same answer (`hand_resolved_pip_sources`). The prune keeps the entry of a package still in its markers whose spec is the block's stored side. A `rejected` line is cleared by editing the package's line by hand (the prune drops the entry) or when the owner moves the line to it. Set `incubacloud.requirements_resync_enabled=0` to restore the old frozen behaviour.

## Endpoints that enqueue

No endpoint refuses a job because the instance is busy: the job waits in its queue ([The job queue](#the-job-queue)). The deploy and rebuild endpoints answer through `_job_response` (`controllers/_data_load/_helpers.py`, reusable by an inheriting controller — a layer's own rebuild may use it): `{job_id, state, job_type, queued_behind}`, where `state` is `queued` when the job waits and the state its `queue.job` reached when it started (`pending` at first), `job_type` is the visible name of its type and `queued_behind` the visible name of the type of the job running on its target (`False` when it started, or when nothing visible runs — a queue held by a failure). A job that waits on a conflict alert answers `{job_id, state: 'blocked', blocked: true, alert_id, alert_code, message, conflicts}` instead. What a job's type allows can still refuse it: a second job of an exclusive type, a sixth entry, a role gate — as `{ok: false, error}` or an RPC error, as before.

The other endpoints that enqueue answer the job's id alone (`job_id`, or `job_ids` for a chain, first step first: backups, restores, PITR, the clone and the refresh from production, the move and its rollback, the host's whitelist, hardening and deletion, the metrics central, the conflict resolutions that put a waiting job back in its queue), as do the ORM calls the panel makes (`cloud.job.enqueue` for the instance's and the host's actions, a retry, and in the restore dialog the upload key, its check and the restore itself). Every button behind them reads the same answer from `/cloud/get_job_state` once its request has committed. The panel turns it into one notice — "Started: <type>", "Queued behind <type>", or "Queued" — with the type's name in the reader's language (`cloud.job.type.name` is translated), and opens no tab: a job's log opens from the job lists, where a waiting job shows its place ("Queued · N ahead"). A move rolled back before its chain started answers no job: cancelling it undid it. The SSH restore's upload key is installed by a job too, and the dialog shows the key at once: while that job waits, the dialog says the command works once it has started. Reviving an archived instance and deleting one keep their own words ("Reviving …: deploying, then restoring its copy"): an archived instance has nothing running to wait behind.

## Secret management

Sensitive fields use the custom `EncryptedChar` field type (a `fields.Char` subclass) backed by Fernet symmetric encryption. The database column always stores the `enc:<token>` form; Python code always sees plaintext.

- The key **must** be set in every environment, and is read from the first of these that is set (`password_utils._read_secret_key`): the **`INCUBACLOUD_SECRET_KEY`** environment variable; the file **`INCUBACLOUD_SECRET_KEY_FILE`** names; the file `secret_key_file` names, or else `secret_key`, in the `[incubacloud]` section of odoo.conf. A place that is set but empty, unreadable or malformed fails rather than giving way to the next one, and the log names the place, never the key. There is no fallback and no plaintext mode: a missing or invalid key makes encrypt/decrypt raise (`IncubacloudCryptoError`) instead of silently writing plaintext.
- A key in odoo.conf is as safe as that file and the server: whoever reads it, with the database, opens every secret. On Odoo.sh the file is copied to the staging and development branches: whoever has a shell on one of them can read the production key, and with a copy of the production database opens every secret, so the key is as protected as the access to the Odoo.sh project. `data/neutralize.sql` deletes the stored secrets from the copy's database, archives the hosts and cancels the pending jobs, but it does not protect the key; whatever is added to the models with a secret or an access to a host belongs there too.
- A key file must be an absolute path to a regular file of at most 64 KiB (`password_utils._read_key_file`); one readable by every user of the server is read with a warning. While no key is usable, a process logs the error and reads the sources again at most every 30 seconds (`_KEY_RETRY_SECONDS`), not on every encrypted field it touches.
- **Key rotation** is built in: every place accepts a comma-separated list of Fernet keys (MultiFernet). The first key encrypts new values; every listed key can decrypt. See `docs/runbooks/RB-01-rotate-secret-key.md` for the full rotation procedure.
- Legacy plaintext values (no `enc:` prefix) pass through unchanged on read, which is what migration code relies on.

**Encrypted fields (16 across 7 models, and `pitr_key` with `incubacloud_pitr`):**

| Model | Fields |
|---|---|
| `cloud.host` | `password`, `key_file`, `traefik_panel_password` |
| `cloud.instance` | `odoo_admin_password`, `odoo_admin_user_password`, `postgres_password`, `smtp_relay_password`, `smtp_relay_oauth_client_secret`, `secret_key` |
| `cloud.backup.backend` | `s3_secret_access_key`, `passphrase` |
| `cloud.github.app` | `webhook_secret` |
| `cloud.settings` | `github_pat` |
| `cloud.terminal.route` | `auth_token` |
| `cloud.host.terminal.route` | `auth_token` |
| `res.users` | `cloud_telegram_bot_token`, `cloud_webhook_secret` |

The frontend cannot read encrypted values directly. `/cloud/get_secret` exposes a whitelisted subset (see `docs/api-endpoints.md`) to developers with write access on the record.

### Each instance's own key, kept by the panel

An instance that runs this module encrypts *its* secrets with the `INCUBACLOUD_SECRET_KEY` in its `.docker/incubacloud.env`. That file used to exist on its host only — `deploy.sh ensure-secret-key` generated it and nothing ever read it back — so an instance moved to another host, rebuilt on a new one or cloned to staging got a new key, and its restored database could no longer read what it had encrypted (two panels, 18-oct-2026). **`cloud.instance.secret_key`** (developer-only, never copied, never in the config snapshot, the copier answers or a job payload) is now the panel's copy:

- A new instance is born with a key. One created already on its host (an import) waits for the host's.
- Every deploy and rebuild (`SecretKeyEscrowMixin._ship_secret_key`) reads what the host holds, **merges** it with the panel's copy (`merge_secret_key_lines`: the host's keys first — the running Odoo keeps its primary — then any the panel has that the host lacks; no key is ever dropped, whichever side is stale), saves the merge, and writes it to the host before `ensure-secret-key`, which then keeps it. During a move the job runs on the target, where nothing exists yet: the key is read on the origin, where the instance still lives.
- The file is staged in `/tmp` created 0600 (`_upload_private_files`) and removed when the job ends, failed or not; it is moved into place 0600. The value is never logged; who changed it is (INFO).
- A staging keeps a key of its own when its copy of production is neutralized (a clone always is): neutralizing clears every encrypted column, so nothing it holds was encrypted with production's key. A refresh left live (`neutralize=False`) keeps production's secrets, so it gives the staging production's keys too and recreates its Odoo.
- Instances deployed before this existed are read once by the daily `cron_capture_secret_keys` (hidden job `capture_secret_key`, which only reads); one whose host cannot be read raises `secret_key_not_escrowed` on the second day.

What this concentrates: whoever holds the panel's database and its `INCUBACLOUD_SECRET_KEY` can now read every instance's key — but already held every host's SSH key and every instance's admin password, so the threat model does not change. The panel's own key becomes the root of trust of the fleet's: it must have a copy off its host (see RB-01).

**An alert on an unreadable secret closes itself.** `cloud.settings._cron_resolve_readable_secrets` (hourly, and once at startup — the right key usually arrives with a restart) decrypts again, from the raw column, every value an active `encrypted_value_unreadable:*` or `secret_rotation_stranded:*` alert stands for: the record itself for a host/instance/project secret, every row of the model linked to the alert's target otherwise. When all of them open, or the rows are gone, the alert is dismissed as the platform and announced resolved (a provider alert reaches its provider). A read in the hot path cannot do this: the process that failed keeps its cached key chain.

### Neutralized copies

A copy of a panel (development, QA, a neutralized download, a staging of a partner's panel) runs `odoo neutralize`, or the series' load tool with `--neutralize` (`ic_db_load_args`), before it is upgraded: each installed module's `data/neutralize.sql`, one statement per file, so one error aborts all of it, Odoo's own included. A column added after the copy was taken is cleared in a block of its own that skips it when missing. What core's file leaves the copy unable to do:

- **decrypt or use a secret**: every encrypted column is cleared, and the hosts and instances are archived;
- **reach out**: the users' webhooks are cleared, metrics are switched off (their URLs then go unread), and the jobs production had not finished are cancelled with the `cloud.job` mirroring each, so none runs in the copy;
- **switch its crons back on**: Odoo switches every cron off, and none of ours declares `active` in updatable data, which the copy's next module update would write again.

`tests/test_neutralize.py` keeps this true. Encrypted fields are checked against the registry, every installed module at once. `NeutralizeInventory` checks a repository's own modules: every stored field whose name says it points somewhere (`url`, `uri`, `endpoint`, `webhook`) is cleared by a script or exempted with its reason, and no updatable cron declares itself active. A layer above mixes it into a test of its own, with its own exemptions, and sets `allow_inherited_tests_method` (Odoo collects only a class's own test methods otherwise).

## Security model

- **5-tier RBAC**: Stakeholder (read-only) → Consultant → Project Manager → Developer → Administrator, implemented as nested groups. `cloud.security.mixin` centralises the gate helpers (`_check_can_deploy`, `_check_can_manage_hosts`, …) used by every endpoint and by server-side `cloud.job` enqueue gating.
- **What a job leaves behind is read by role**: every role that sees a job reads the panel's own messages of its log (`source='system'`); its raw output (`stdout`/`stderr`) and its files (backups, neutralized copies and exports, attachments of the `cloud.job`) are a Developer's and an Administrator's, who read logs and handle backups (`rule_job_log_chunk_*`, `rule_attachment_job_files*` in `security/cloud_rules.xml`). A Project Manager sees every job, with the panel's messages only. The MCP and the assistant read logs and files under the same rules.
- **Job actions are authorised at enqueue, per type**: `cloud.job._get_job_type_min_group()` maps every job type to the minimum role allowed to ask for it (lifecycle/deploy → Consultant; backups/restores/exports → Developer; host-level, observability and host-move → Administrator), enforced in `_check_job_type_allowed` on `enqueue`, `enqueue_chain`, `retry_job`, `unblock_and_enqueue` and `cancel_job` (in every state, on the job and on every step its cancellation ends). The map is fail-closed — an unmapped code requires Administrator — and a structural test (`test_job_type_gate_invariant.py`) fails the build if a declared job type is missing from it, so a new type cannot ship ungated. Extending modules add their own types by overriding `_get_job_type_min_group()`. `delete_instance` additionally escalates to Administrator when the target is a production instance, *before* any remote command runs. Executors are trusted readers of the host connection material (the job runs under the enqueuing user's env, and the SSH endpoint/credential fields are Developer-gated at the ORM): the elevation lives in the executor constructor, `get_transport()` and the Ansible inventory — never in `ssh_connect_kwargs()`, which is public and returns the password.
- **Record rules** scope projects/instances/jobs/alerts to project members; global alerts are hidden from the lower tiers.
- **What a member writes is not all theirs** (`cloud.instance._check_guarded_vals`): a consultant writes their projects' instances, production ones included, but only the platform writes a move's markers (which jobs a rollback and the watchdog cancel, and where the cleanup runs — and a move's chain is only its instance's jobs, `_get_move_chain_jobs`), a pull request preview's identity (what the GitHub webhook rebuilds and deletes by) and the removal and purge stamps; only an administrator sets an instance's directory on its host and the place of its copy (what a teardown removes and a purge empties), changes the host of an instance past draft (its stack is there and its waiting jobs follow it; `move_to_host` moves both), or renames a project's remote folder (which names its instances' directories). Where an instance's or a project's backups are kept is a Developer's choice, as backups are. Creating an instance already past draft is an import, an administrator's, and so is `delete_archived`, which without a copy removes the record as the platform. No project, the platform's included, takes a remote folder the platform keeps on every host (`RESERVED_REMOTE_FOLDERS`: the proxy, the shared whitelist, the instances a module on top keeps in reserve and the observability stacks), by its folder or by the name it is derived from; a layer that derives folders from names of its own refuses them there too. Whether an instance is production is chosen when it is created and no person changes it afterwards, an administrator included (`/cloud/save_instance` refuses a change with its reason): it decides who may delete the instance and whether its egress is filtered.
- **A repository URL names github.com, and only it gets the token (5-nov-2026).** The build clones every repository line with the panel's GitHub token (the App's installation token or the PAT) in its URL, and `deploy.sh record-heads` asks each one's head with it. The token used to go to any URL that contained the text `github.com` (`"github.com" in url`), and a URL that could not be parsed still got the App's token or the PAT, so a line such as `https://evil.example/github.com/x.git` would have sent it to that host. Now `cloud.repo.mixin` (both `cloud.project.repo` and `cloud.instance.repo`) stores only `https://github.com/<owner>/<repo>` or its `.git` form (`is_safe_repo_url`): `create` and `write` first rewrite the other spellings of a github.com repository (`git@github.com:`, `http://`, no scheme, `www.`, any ASCII case of the host, a final slash, blanks) into it (`canonical_repo_url`), and the constraint refuses everything else, including the query, fragment, tab and newline the earlier check (`[^/]+` after the owner) let through. Every way in (the panel's routes, which the MCP and the assistant call, the imports from GitHub and from a host, the lines of a module on top) ends in those two methods. The executor gives a token only to a URL that passes the same check once canonical (`_get_token_for_repo` answers `None` otherwise, `_github_authed_url` injects nothing), so a row stored before the check existed is cloned without one, and an old spelling of a github.com repository is cloned from its canonical URL. `remote_ref_head` does not ask a URL whose credentials would go to any host but `https://github.com` itself, nor one with a `?`, `#` or `\` before its path, where parsers disagree on which host it names. The host import keeps a remote as `canonical_repo_url` spells it (it used to turn `git@gitlab.com:x/y.git` into `https://github.com/x/y.git`). No migration rewrites the stored lines: those checked on that date were all canonical already, a line the panel saves is rewritten with its URL, and any other write to a line (its branch, its pin, as pinning, a pull request's webhook and a module on top pinning core do) stores its old spelling canonical too; a URL that cannot be made canonical fails that write with the constraint's message until someone corrects it.
- **Audit trail**: `cloud.audit.log` records who did what, filterable per instance/host, with configurable retention and a manager-only purge.
- **Rate limiting**: DB-backed counters protect the public endpoints (webhook, health), the restore upload and terminal opens. Caps are tunable in Settings → Rates.
- **Web terminal**: PTY subprocesses are isolated per session with an encrypted routing token; only the owning user can attach. Idle sessions are reaped (see RB-03).
- **Host shell**: a login shell on the machine itself, for Administrators only (`_check_can_manage_hosts`) — the role that already runs root there through every host job, with the same key. Same subprocess isolation as the web terminal, its own cap (3/min per user and per host), one open session per user and host, and an immutable `cloud.host.session` row per session. What is typed is not recorded: a shell receives passwords on stdin. Only `host_terminal_session.py` may open a command-less PTY; `test_terminal_session.py` fails the build if one appears anywhere else.

### Who may open SSH on a host

The hardening ruleset admits SSH from two named sets, one per address family -- `inet filter ic_ssh_allow` (IPv4) and `ic_ssh_allow6` (IPv6), since a set holds one type of address -- filled from the panel's address, the address the play connected from, and `allowed_ssh_ips`, like the CDN sets: a named set can change without Ansible and without reloading the ruleset. A family with no address keeps its set, empty; the catch-all `0.0.0.0/0` (the panel's address unknown and `allowed_ssh_ips` empty) opens IPv6 too. `cloud.host._ssh_allowlist_change(op, ips)` runs `scripts/ssh_allowlist.sh` on the host — the list split by family and both sets replaced in one nft transaction, the whole list never left empty, and both sets rewritten in `/etc/nftables.conf` after the live change worked (the file parsed with `nft -c` first; the CDN sets' stale lines there are left alone) — and keeps the change in `allowed_ssh_ips`, which the next hardening rebuilds the sets from. A host hardened before the sets existed has its list inlined in the rule, and one hardened before 27-oct-2026 the IPv4 set alone: the first change brings either to both sets, live (sets created, rules replaced or added by handle) and on disk. `auto-merge` lets a catch-all load beside an address. A layer may use it to move a panel's own servers with the panel (the old host is the only one they admit until told otherwise).

The list a hardening applies comes from the panel's address, the address the play connects from and `allowed_ssh_ips`; nothing writes the list by itself. The panel's address is `cloud.host._hardening_panel_ip()` — none in core, the panel's own public address in a layer that knows it — and every layer's executor seeds the list with it. The address of whoever asks for the hardening enters only by the dialog's **Also allow my IP**: `/cloud/preflight_host_hardening` says who will be able to open SSH and whether that address can be offered (`cloud.host._ssh_access_preview`: a public address, or one of the host's LAN; never a proxy this panel believes, by its settings or by `x_real_ip_trusted`; of the host's address family), and `/cloud/apply_host_hardening` checks the address it is sent against the one it sees before writing it, in the savepoint that queues the job. A host whose SSH an edge this panel does not govern closes (`_ssh_closed_by_foreign_edge`: a server whose firewall another panel governs) is offered nothing. Until 27-oct-2026 a layer filled an empty list with the asker's address before every hardening, unannounced: an IPv6 a host reached over IPv4 could not use, and on one host an address of the CDN.

### Host edge protection (network layers)

How a host is reached decides what can defend it, and that is a **property of the host** (`cloud.host.behind_cdn`), not an assumption. A host reached **directly** — its domains resolve straight to its address — can only be defended on the box itself, and that is how hosts run by default, because a proxied name cannot answer the TLS challenge a host uses to obtain its own certificate. A host reached **through a CDN** is defended at the edge instead, and its own layers change shape accordingly.

Getting this wrong in either direction is expensive, and both mistakes have been made here. Shipping CDN ranges to a host reached directly turned its per-visitor rate limit into a single bucket shared by every instance on it, because `ipStrategy` reads a forwarded chain that direct traffic does not carry (2026-09-03). Refusing direct traffic on a host whose visitors arrive directly would take it off the internet outright.

The protection is layered, outermost first:

1. **Provider L3/L4 anti-DDoS** — volumetric and protocol floods are absorbed upstream in the provider's network. Hetzner and OVH both include this free and automatically. It is an **assumed dependency, not our code**: a host on a provider without it loses the volumetric layer entirely, and such a provider should not front public instances (or must add one, e.g. Cloudflare Spectrum). See [RB-18](runbooks/RB-18-tune-host-edge-protection.md).
2. **Host connection-rate cap (nftables)** — a per-source new-connection limit on 80/443 in the hardening ruleset (`ansible/playbooks/host_hardening.yml`), on the **forward** hook because the instances' traffic is DNAT'd to the Traefik container and never touches the input chain. On by default since 1.0.183 at 50 per second (`cloud.host.http_conn_rate`, passed to every hardening run), after it shipped off from 2026-08-14 — when an unrehearsed drop on that hook took the fleet down — until rehearsed. It weighs only the first packet of a connection redirected from the host's 80/443, with the same guards as the CDN allowlist below; matched on `tcp dport` alone it also counted the containers' own outbound traffic.
3. **Proxy per-IP rate limit (Traefik)** — a `rateLimit` middleware attached as the https entrypoint default (`data/traefik/config.yml`), so it throttles every instance on the host by client IP before a request reaches Odoo's pbkdf2 login. This is the principal control against the asymmetric login-DoS of SEC-008 applied to the instances' sites: one middleware covers N instances because it keys on the source IP, not the instance. Tunable live (the host's `config.yml` is watched); see [RB-18](runbooks/RB-18-tune-host-edge-protection.md).
4. **Login limit (Traefik)** — the general limit is the same for every path, which still lets one address try 300 passwords a minute, and Odoo's own cool-down counts per worker process. Each instance's override (`DeployInstanceExecutor._login_router_labels`) adds a login router beside each of its routers: POSTs to the endpoints that check a password (`/web/login`, `/web/login/totp`, `/web/session/authenticate`, `/web/reset_password`, `/xmlrpc/2/common`), with the host's `loginlimit` middleware first (20 a minute, burst 10) and otherwise the middlewares the template gives the router it shadows, so the login is never less protected than the rest of the site. Priority 15: above the template's routers for those paths (the `/web` one is 10), below any router a deployment layer sets in front of an instance's paths (30 and up). This repeats the template's router scheme on purpose, like the staging middlewares beside it; should a template release rename it, Traefik drops the login router alone and the login falls back to the template's — see [RB-15](runbooks/RB-15-bump-copier-template-pin.md).
5. **Ban on repeated failed logins (fail2ban)** — a jail bans for an hour an address that fails ten web logins in ten minutes, in fail2ban's own nftables table on the **forward** hook and on 80/443 only. It reads the proxy's access log, not Odoo's: Odoo writes the login it was sent as-is, and a login carrying a newline forges whole log lines, so the jail could be made to ban anybody; Traefik writes one JSON object per request and escapes what the client sent. A form login that fails is answered 200 (the form drawn again) and one that succeeds is redirected; the RPC logins answer 200 either way and are left to layer 4. Off behind a CDN, where the connecting address is the CDN's; and whatever the proxy trusts as a proxy is exempt, since a failed login arriving through one is the visitor's. The jail has a chain of its own (`f2b-weblogin`) in fail2ban's table: the action's default chain is the one the sshd jail creates on the input hook wherever the distro bans with nftables (Ubuntu 24.04), and a chain cannot sit on two hooks — with the default name the web-login rule landed in the input chain, where DNAT'd instance traffic never passes, and banned nothing (measured on 24.04).
6. **Application counters (`cloud.rate.limit`)** — DB-backed per-user/per-IP caps on the panel's own public endpoints (webhook, health, terminal, logs). See [RB-04](runbooks/RB-04-tune-rate-limits.md).

Layers 1–5 protect the **instances**; layer 6 protects the **panel**. All of this is **core**: a partner hardening their own VPS inherits the same defaults, chosen to be safe for any host rather than tuned to our pool.

**Behind a CDN, layers 2 and 3 change rather than stack.** Layer 2 becomes an explicit allowlist of the CDN's ranges on 80/443 instead of a per-source cap — behind a proxy every visitor arrives from a handful of edge addresses, so a per-source cap would throttle the CDN and protect nobody, and a host behind a CDN gets no cap at all, closed or still open at the origin — a host between moving its names and closing its firewall is open, and its visitors already arrive from the edges. The list sits on the same **forward** hook as the cap it replaces, because that is the hook DNAT'd instance traffic crosses (the same list in the input chain alone lets everything through — measured), and it judges only the first packet of a connection redirected from the host's 80/443 (`meta l4proto tcp ct state new ct status dnat ct original proto-dst`; the protocol first, because nftables 1.0.2 cannot type `ct original proto-dst` without it), so replies and the containers' own outbound traffic are never weighed against it. A name that resolves straight to such a host, bypassing the CDN, stops answering — ACME challenges included. Layer 3 keeps the same middleware but keys it on the forwarded chain (`sourceCriterion.ipStrategy.depth: 1`), which is only correct *because* the chain is now always present and always written by a proxy Traefik has been told to believe (`forwardedHeaders.trustedIPs`). Neither switch is inferred: they turn on `behind_cdn`, and the firewall half additionally waits for `block_direct_access`, so the two cannot be enabled in an order that leaves the host answering nobody.

**Refusing direct traffic is checked, not assumed.** `block_direct_access` has two halves and only the proxy's lands by itself (Full Setup, the trusted-proxies push): the firewall's needs a hardening run, which nothing starts on its own, so the setting can say "closed" while the origin answers anybody. Nothing watched either half: in October 2026 a host stayed open at its origin for weeks, and the hardening changes of the twelve days before reached no host. An hourly cron (`cron_check_host_posture`, `models/cloud_host_posture.py`) asks two things. **`host_origin_open`**: the panel connects straight to every host behind a CDN that refuses direct traffic, its proxy deployed, asking for a name the host serves on 443 and then 80 (its own `curl --resolve`); any connection let in — a page, the proxy's 403 — is an alert naming what answered, confirmed over two runs (`cloud.alert.policy`). Only a connection left unanswered until the wait runs out reads as closed, and only once the same name answers through the CDN on 443: silence is the healthy reading, so a panel whose egress drops everything (out only through a proxy, inside a perimeter that discards direct connections) would read every host as closed, and that control, per host and on a visitor's own path, tells the two apart. A connection refused (the firewall let it through to a proxy restarting or down), an unreachable address, a drop while the CDN is out of reach, or a drop at a host that serves no name yet decides nothing for that host that run: nothing is raised or cleared. **`host_hardening_outdated`**: each successful hardening records what it applied — a fingerprint of the playbook without its comment lines (`hardening_recipe`) and whether 80/443 were limited to the trusted proxies (`hardening_cdn_only`) — and a hardened host whose record disagrees with the recipe this panel ships, or with what its settings ask for now, is told to re-apply it. Both say who can act and how, neither re-runs anything (that touches a live host), and both clear themselves. A failed hardening, for its part, is one alert: `hardening_failed` carries what failed, and `job_failed` is not raised beside it (the executor's `_failure_alert_code`, honoured by `cloud.job._create_job_failed_alert` for a type whose failure does not hold its queue).

**The CDN's addresses are not ours alone.** They are shared by every customer of the CDN, so an allowlist of them admits anybody's zone pointed at our origin, past every rule of ours. A host behind the CDN with direct access refused can therefore be given the authority its client certificate is signed by (`cloud.host.cdn_client_ca`, or a deployment layer's `_effective_cdn_client_ca`): the proxy then requires that certificate on every TLS connection (`tls.options.default.clientAuth`, `RequireAndVerifyClientCert`, in `dynamic/tls-client-auth.yml`, shipped by Full Setup and the proxy-settings push like the default certificate). Cloudflare calls this Authenticated Origin Pulls; with the zone's own certificate rather than Cloudflare's shared one, only that zone gets through.

**Certificates follow the same fork.** A host reached directly obtains its own through ACME. A host behind a CDN is *given* one — `tls_default_cert` / `tls_default_key`, served as Traefik's default certificate — because the challenge cannot reach it. In this platform that is one origin certificate for the whole zone, held in settings and handed to every host marked as being behind the CDN; in core it is simply a pair of fields, so a partner can supply a certificate from any source — pasted on the host's Traefik tab, where the pair is refused unless it matches (half a pair, an unreadable PEM or a key from another certificate would make Traefik answer every handshake with a throwaway), and shipped by *Push Trusted Proxy Settings* or *Full Setup*.

Each domain then says how its router gets a certificate (`cloud.instance.domain.cert_resolver`), and only the default defers to the host. **`auto`** (the default) asks the host per name: its held certificate when a CDN answers for the name *and* the certificate covers it, ACME otherwise. **`letsencrypt`**, **`custom`** (the held certificate, whatever the host) and **`none`** are explicit choices a host never overrides. Copier only ever receives the resolved value — `letsencrypt`, `true` or `false` — never `auto`. Every deploy and rebuild writes one line per domain saying what its choice resolved to, and refuses `custom` on a host that holds no certificate — neither a default one nor one declared by hand in its `config.yml` (RB-12) — before anything reaches the host. The endpoint that saves an instance reads the options from the field itself: a copy of the list kept there once lacked `auto` and quietly rewrote it to `letsencrypt` on every save.

### Odoo's information page, refused at the edge

Odoo answers `/website/info` to anyone, with the list of installed apps and the exact version: a stranger learns which known flaws to try. Since 1.0.214 (decision of 7-nov-2026) every host's proxy refuses it on every instance, the existing ones included, before any instance sees the request.

The refusal is a document of the proxy's own, `~/traefik/dynamic/ic_guard.yml` (`models/cloud_host_edge_guard.py`), the same on every host: a router on the `https` entrypoint whose only middleware is an `ipWhiteList` admitting no address (`255.255.255.255/32`), with `noop@internal` as its service, so Traefik answers 403 itself, as `direct-deny` does. Traefik 2.11 has no middleware that answers a fixed status, and a 404 would need a backend. Its rule covers the page bare, with a trailing path and behind a language code, which Odoo reroutes to the same page (`/es/website/info`):

```
Path(`/website/info`) || PathPrefix(`/website/info/`)
  || Path(`/{lang:[A-Za-z0-9_@-]{2,20}}/website/info`)
  || PathPrefix(`/{lang:[A-Za-z0-9_@-]{2,20}}/website/info/`)
```

Traefik matches the decoded, cleaned path, so `/website/%69nfo`, `/es/website/%69nfo` or `//website/info` are refused too (measured on 2.11.44 and 2.11.61). `http` redirects to `https` on the entrypoint, before any router. The entry points are named because Traefik 2.11 hangs a router without them on every one, `direct` and `metrics` included, and `tls: {}` keeps the `default` options, so the CDN's client certificate still applies. The underscore in the file's name keeps it apart from the `{name}.yml` documents a deployment layer may write beside it: the names it gives them cannot hold one.

| Router (on `https`) | Priority |
|---|---|
| The template's `main` | 1 |
| The template's `/web` and `/website/info` router (`forbiddenCrawlers`) | 10 |
| Login limit (`LOGIN_ROUTER_PRIORITY`) | 15 |
| The template's websocket router | 20 |
| Routers a deployment layer puts in front of an instance (parking, refusing, draining) | 30 to 1000 |
| **Edge guard** (`EDGE_GUARD_PRIORITY`) | **2000** |
| **An instance's exception** (`WEBSITE_INFO_EXCEPTION_PRIORITY`) | **2010** |
| `direct-deny` (`direct` only) | 10000 |

Above everything an instance carries, so a sleeping or parked instance refuses the page without being woken, and a draining one answers 403 instead of its restart page.

**Who writes it.** Full Setup writes it before the proxy starts (`Install the edge guard`, with `--no-mount-check --no-probe`: the proxy neither runs nor mounts the directory yet), and the step is fatal: a Full Setup that did not write it fails, or every instance would serve the page with nothing saying so. A host set up before gets it from `push_edge_guard` (`scripts/edge_guard.sh`): the file replaced only when it differs, atomically, with `sudo -n` when the directory belongs to root; then the proxy must mount the directory (exit 3, the file stays written, a warning `edge_guard_not_mounted` until a run finds it mounted or a Full Setup) and is asked for the page on 127.0.0.1 (403 exits 0; a handshake the CDN's client certificate refuses, code `000`, exits 4, "not verified", only in the log; a real HTTP answer other than 403, such as 200 or 404, exits 5 and fails the job, because the guard is not applied, say Traefik dropped the file). The proxy is never restarted: the file provider watches the directory. The update to 1.0.214 queues the job once per active host whose proxy the panel set up (`end-migrate.py`: `end`, so every module's hook has been loaded), never a Full Setup. The host Check stays read-only: its playbook exports the file's `sha256sum`, and the job is queued only when the file is missing or differs from the render. What a host's proxy reads is recorded on it (`edge_guard_shipped_hash`, `edge_guard_shipped_at`).

**Who is left alone.** `cloud.host._edge_guard_leaves_alone()` is `False` in core. A deployment layer whose own panel is served by one of its hosts' proxies, set up by hand, can exclude that host there; the update, the Check, Full Setup and the job all ask it. Core and the deployment layer therefore go out in the same deployment: the update asks the hook, and a core deployed alone would queue the guard on that host too.

**The exception.** An instance with `website_info_public` (off by default, not copied to a staging, audited) carries, in its compose labels, a router per group of its names (redirects aside) with the guard's rule behind its hosts, at 2010, to its own `-main` service and with the middlewares the template gives its `forbiddenCrawlers` router, with its TLS twin (`DeployInstanceExecutor._website_info_router_labels`). Labels rather than a file of the host's: they go with the containers, so a deploy, rebuild, move or revive writes them from the field, a rebuild with it off drops them and a deleted instance leaves nothing behind. While the instance sleeps or is stopped, its labels are gone and the guard answers. The config snapshot carries the field only while it is on, so the fleet's hashes did not move with the release; switching it shows the instance's changes for a rebuild.

**What it costs.** Internal users lose the page too: the proxy does not know who is signed in. The refusals are counted under the guard's router and `noop@internal`, not under an instance. Instances with Website keep listing the page in their sitemap; crawlers get 403. The `direct` entrypoint does not carry the guard: it admits only the platform's own peers and refuses everything without a router of its own.

### The direct entrypoint

Some traffic is the platform talking to itself: agents pushing metrics, panels calling their manager. A CDN in front of it adds a detour and a dependency, and the host behind the CDN refuses everything else on 443. So a host can open a second entrypoint, `direct`, on a port of its own (`direct_port`). It trusts no forwarded header, keys its rate limit on the connecting address, requires no client certificate (its TLS option is `direct`, not `default`) and admits only the addresses on the host's direct list, in nftables (`ic_direct_v4`, on the forward hook like the CDN sets) and in Traefik (`direct-peers`, the entrypoint's first middleware). A router at priority 10000 refuses the rest: Traefik 2.11 attaches a router without entry points to all of them. It answers 403, or 421 from Traefik 2.11.47 on, which refuses at that router before its list a connection negotiated with the `direct` options (the router has no domain, so it keeps `default`); hosts pull different 2.11 releases, so the probe of a direct name takes either (`GET:/flags:403,421`). Its certificates come from the `direct-dns` resolver; names on it must not be covered by the host's default certificate, or the ACME prune would retire them.

One Traefik serves 443 and the direct port, so the direct entrypoint also caps new connections per source in nftables and carries its own read, write and idle timeouts. Behind it, Odoo's `remote_addr` is the connecting host's own address, not a CDN edge.

### Host maintenance window (04:00 UTC)

Hardening enables `unattended-upgrades` on every host it touches, and when the host has `auto_security_updates` set it also allows an automatic reboot, pinned to **`Automatic-Reboot-Time "04:00"`** (`ansible/playbooks/host_hardening.yml`). So a host that needed a kernel or `openssh-server` update disappears for a minute or two just before 04:00 UTC — sshd restarts mid-upgrade, then the box reboots — and comes back on its own. A production host did this five times in six weeks (July and August 2026).

This is normal maintenance, not an incident, and the monitoring is sized for it: the SSH probes retry a transient connection failure ten times about thirty seconds apart (`AbstractExecutor._connection_retry_attempts`), so ~10 minutes of unreachability pass without alerting anyone. `host_unreachable` is raised only once a probe has actually exhausted that budget and reached a terminal state — never from a mid-flight guess about which attempt was the last.

When planning around it: the window is per host and only fires when an update demands a reboot, so it is not a schedule you can count on, only one you must not be surprised by. To move it, change the pin in the playbook and re-run hardening; to disable the reboot entirely, clear `auto_security_updates` on the host and patch it on your own schedule.

## GitHub integration

IncubaCloud supports GitHub App authentication for private repository access and receives webhooks for installation, push and pull request events. A stored PAT (in `cloud.settings`) is the fallback when no App is configured.

### Authentication flow

```
1. User opens Settings → GitHub App
2. GET /cloud/github/setup
   → Generates App manifest (branded, fleet-unique app name)
   → Redirects to github.com/apps/manifest-code

3. User installs app on GitHub org
   → GitHub redirects to GET /cloud/github/callback?code=...
   → Exchanges code for (app_id, private_key, webhook_secret, owner)
   → Stores in cloud.github.app (singleton), owner_login included

3b. The installation id
   → installation.created on the App owner's account: taken from the webhook
   → on any other account: a manager takes it with Check installation
     (/cloud/detect_github_installation), which names the account

4. On each API request needing auth:
   → Generate short-lived JWT (10 min) from private_key
   → Exchange JWT for installation token (1h) via GitHub API
   → Cache installation token in memory (per worker process)
   → Use Bearer token in API requests
```

### Webhooks and auto-rebuild

All webhook events are stored in `cloud.github.event` (immutable audit log). The receiver validates the HMAC-SHA256 signature, rate-limits per IP and ignores replayed delivery ids.

`push` events drive **auto-rebuilds**: an instance rebuilds when it is active, deployed, has `auto_rebuild` enabled and its host is active. A push always queues its rebuild (`last_auto_rebuild` is written then): on a free instance it starts at once, behind a running job it waits in the instance's queue, and while the rebuild of an earlier push waits it merges into that one instead — the waiting job's `coalesced_pushes` grows with it and its head stays the first push (`RebuildInstanceExecutor._merge_queued_payload`), so no commit is built twice and none is dropped. A rebuild someone asked for by hand, or one already dispatched, is never merged into. A push after a rebuild that failed is not held by that failure: its rebuild starts as the fix it usually is (see *A failure holds the queue* above). Per-repo **freeze** flags are honoured. Archived instances and archived hosts never auto-rebuild.

### Pull request previews

`pull_request` events arrive through the same receiver and are handled by `cloud.github.event._process_pull_request_event`. The head ref is checked with `is_safe_git_ref` first: it ends up in `cloud.instance.repo.branch`, so a hostile ref name is dropped here rather than at the constraint.

**Only the panel's pull requests (1.0.223).** An event whose `installation.id` is not the panel's installation is ignored (`_is_own_pull_request`), whatever its action. A preview is cloned only from a production whose own repository lines (`cloud.instance.repo`) follow the pull request's **base** repository (the one it is opened on), both URLs compared in their canonical form (`repo_url_key`), and never for a pull request from a fork — a head repository other than the base, or one deleted (`_pr_preview_sources`): a preview carries a copy of production's data, and a fork's branch is code written by someone without access to the repository. Fork pull requests never had a preview: their head is the fork, which no production follows. The instance's lines decide, not the project's: a project's lines are the template its instances start from, and an instance often follows repositories they do not list; below Project Manager nobody can change a line's URL, so they are as safe a source. The same rule binds the installation webhook: `installation.created` is taken as the panel's installation only on the account that owns the App (`cloud.github.app.owner_login`, kept by the manifest callback); any other waits for a manager's Check installation. An App set up by hand, or before 1.0.223, has no owner kept, and its installation is always the manager's to take.

- **`opened` / `reopened`** — every `cloud.instance.repo` matching the base repository with an **empty `commit_sha`** (a pinned repository never takes part), on a `production`, deployed instance whose project has `pr_reviews_enabled`, yields a candidate. Each candidate is put to `_pr_preview_allowed(inst)` — yes by default; layers on top override it to keep instances they manage themselves out, the same pattern as `_rebuild_job_type`. Deduplicated on `(pr_number, pr_repo, project)`, the instance is then cloned with `clone_to_staging('pr-<n>', …)` inside a savepoint, so a clone that fails half-way leaves no row behind to be mistaken for an existing preview.
- The clone lands on the **production's host**, follows the pull request's branch on the matching repository, gets its domain from the host's wildcard like any other instance (`create()`), and runs the chain `deploy_instance` → `backup_download` (on production; always a live dump — `latest` failed on a production with no backup yet) → `restore_instance` with `neutralize` and `reset_base_url`. The restore's success posts the "ready" comment (`cloud.instance._pr_preview_ready_body`) through the GitHub App.
- **`synchronize`** re-points the branch and enqueues a rebuild, skipping archived instances and inactive hosts. **`closed`** deletes the comment and enqueues `delete_instance`, or unlinks a preview that never deployed.
- **Failure is reported where people look.** A `UserError`/`ValidationError` from the clone is commented on the pull request verbatim and raised as a `pr_preview_failed` warning on the production instance; anything else is logged with a reference and published only as a generic line, because the repository may be public. The alert is resolved by the next preview created for that production. Commenting is best effort and never fails the event.

`pr_reviews_enabled` defaults to **off** and travels through `/cloud/get_project`, `/cloud/create_project` and `/cloud/save_project`. Everything the webhook enqueues is signed by the platform bot (`as_platform`), not by whoever opened the pull request.

## GitLab webhooks (1.0.221, 8-nov-2026)

- **Models.** `cloud.gitlab.hook` (one per provider, scope and path; `hook_key` of 32 hex characters so no key starts with a word a proxy in front of the panel may block; encrypted `secret`; `remote_hook_id` when the panel created it) and `cloud.gitlab.event` (`delivery_key` = `Idempotency-Key`, `semantic_key` = `push:<path>:<ref>:<before>:<after>` for pushes, a `summary` without e-mail addresses, never the body). Two partial unique indexes created in `init` make a repeated delivery fail on insert; the receiver answers it 200. The last delivery is read from the events, never written on the hook, and the hook's `state` is written only when it changes: a delivery turns a `pending` or `failing` webhook `active` (resolving `gitlab_hook_failing`), never an `orphan`, so a webhook no line uses is deleted after its 7 days even while pushes reach it; the daily check turns an orphan used again `active` if it had deliveries, else `pending`.
- **Receiver.** `controllers/gitlab_webhook.py`: per-IP bucket through `consume_quota` (READ COMMITTED), 8 MB per route, key and token checked before the body is read (401), then everything is 200. `_dispatch_safely` runs the dispatch in a savepoint and keeps a failure on the event (`error`, `processed=False`); the daily `cron_purge_gitlab_events` dispatches it again, up to 3 attempts in all, and a manager can with `/cloud/reprocess_git_event`. GitLab never retries a delivery and counts error answers towards disabling the webhook, hence no 500.
- **Shared with GitHub.** `cloud.repo.event.mixin` carries `_rebuild_job_type`, `_pr_preview_allowed` and `_rebuild_for_push`; a module that extends the panel overrides the mixin, and neither event model redefines the first two. Each instance's enqueue runs in a savepoint. `_merge_queued_payload` absorbs a push already in the waiting rebuild's list by `(push_repo, push_branch, push_sha, push_provider)`, an empty provider meaning GitHub. Deliveries may arrive out of order; the rebuild reads the branch head when it runs.
- **Verify.** The route records `verify_requested_at` on a READ COMMITTED cursor, committed before GitLab is called (one stamp per 15 s, atomic), asks GitLab for a `tag_push_events` test and returns; the SPA polls `get_git_hooks`. No request waits for another request's insert. The daily check logs a 403 (a credential without the Maintainer role) and leaves the webhook's state as it was.
- **Registering and rotating hold the row (8-nov-2026).** `register_git_hook` and the rotation of the secret each run on a READ COMMITTED cursor of their own that holds the webhook's row `FOR NO KEY UPDATE` while GitLab is called, and commit at the end: a second registration waits and adopts the first's webhook (before, with the row there and no `remote_hook_id`, two at once created two webhooks, and Odoo's retry of a serialization failure did not stop it), and a rotation never writes GitLab over a registration. Rotating writes the new secret and flushes it on the rotation's cursor before GitLab is called, and keeps it only once GitLab took it (a failure rolls it back, and after the `PUT` only the commit is left); on an unclear answer (timeout, dropped connection, 5xx, a 2xx whose body could not be read) the panel sends the secret it keeps again, best effort, and when that fails too it says to rotate again once GitLab answers. Deleting with a credential GitLab refuses (401, 403) deletes in the panel only, as without one, and says so. Deleting a webhook, by hand or by the orphan sweep, resolves its `gitlab_hook_failing` and `gitlab_repo_moved` alerts.
- **Time the row is held (8-nov-2026).** The calls to GitLab under that lock (up to 4 when registering, 2 when rotating) share one budget, `GITLAB_BUDGET_S` = 30 s: the client starts no call past it and waits no longer than what is left (`GitLabClient(deadline=…)`), on top of its 20 s per call. Why a total and not only the per-call timeout: four calls at 20 s each kept the row, and with it the deliveries that turn a `pending` webhook `active`, «Verify» and the other registration, for over a minute. The name's resolution is not inside the budget: Python's `getaddrinfo` takes no timeout, and bounding it would take a thread per call in `net.outbound`, which every Git connection of the panel shares; the system resolver bounds it instead (glibc's `timeout:5` and `attempts:2` per server by default, the panel's container at Docker's embedded DNS), under the `any` policy at each call's connection, under `public` once, when the client is built. Before the answer and before each block of its body (16 KB, read with `read1`, so one socket read each) the socket's timeout is reset to what the budget has left, and past it the call fails with `timeout`; so each wait ends by the budget and a server that answers byte by byte cannot keep the call open past it (the name's resolution aside). A budget spent before the request is sent fails with `budget`, which is clear (nothing was sent); spent after it, `timeout`, which is unclear. A TLS error in the handshake is `tls` (clear, nothing sent); one after the request went out (the session cut while the answer is read) is `unreachable`, unclear like any dropped connection.
- **Merge request previews (1.0.224, 10-nov-2026).** A `Merge Request Hook` is handled by `cloud.gitlab.event._process_merge_request` under the rules of GitHub's previews: only the webhook's own deliveries (its `X-Gitlab-Token`), only a merge request whose `source_project_id` is its `target_project_id` and the webhook's project (`_from_fork`; one naming no source counts as a fork), and only from a production whose own `cloud.instance.repo` lines follow `(provider_id, repo_path)` of the project, unpinned, deployed, with `pr_reviews_enabled` and `_pr_preview_allowed` (`_mr_preview_sources`); the project's lines do not decide. `open`/`reopen` clone `mr-<iid>` with `clone_to_staging(…, pr_provider_id=…)` in a savepoint, one per project; `update` with `oldrev` (new commits) re-points the line and rebuilds through `_rebuild_job_type`, any other `update` and the approvals do nothing; `close`/`merge` write `pr_state='closed'` and queue the note's job outside the savepoint of the delete, then `cloud.instance._remove_closed_preview` unlinks a preview never deployed (`draft`) and enqueues `delete_instance` for any other, unless one waits or runs (10-nov-2026: a preview in `deploying` was unlinked, which its running job refused; the error was swallowed and the preview lived on with its «ready» note). The delete waits for the job running then — the clone's deploy — and cancels what waits, the rest of the chain with it. Guards of a closed preview that is still active with no delete queued: the restore's `on_success` and the note's job queue it. GitHub's `closed` takes the same path (the same unlink was in production). A lost race (serialization failure, deadlock, lock not available: `_concurrency.is_concurrency_error`) is never kept as the event's error, it reaches Odoo's retry of the request; any other failure of one preview is logged and the others go on. In `update` the first is raised at the end, which undoes the rebuilds queued, so the event keeps `error` and the daily cron dispatches it again whole. In `close` the failures are returned, not raised: the closed state, the note's job and the deletes already queued stay (the savepoint of the dispatch is not rolled back), and the event keeps `error` and `processed=False` for the cron, which deletes what is left; raising would let a restore running meanwhile see the preview open and announce it. A group's webhook does nothing for a merge request of a project with an active webhook of its own: GitLab delivers to both, and each would clone and rebuild. Two `open` at once: the loser of `unique (project_id, name)` reads on a READ COMMITTED cursor whether the winner's preview is there and then says nothing. An `open` dispatched after a processed `close` of the same merge request (by GitLab's `updated_at`, else by the order recorded) does nothing. A closed preview does not count as existing, so closing and reopening at once clones `mr-<iid>-2` while the first is deleted. The preview keeps the GitHub fields (`pr_number` = `iid`, `pr_repo` = the project's path, `pr_head_branch`, `pr_comment_id` = the note's id) plus `pr_provider_id` and `pr_state`; GitHub's searches add `pr_provider_id = False`, so a pull request and a merge request of one name and number never meet. A clone that fails raises `pr_preview_failed` on the production; a merge request from a fork that some production would have previewed gets a note saying why.
- **The merge request's note is a job (1.0.224, 10-nov-2026).** `cloud.gitlab.mr.note._job_reconcile`, a queue_job method on `root.bg`, never a call inside the delivery: GitLab cuts a delivery at 10 s and counts errors towards disabling the webhook. It is queued in the transaction that opens, rebuilds or closes the preview, and by the restore's `on_success` on its durable cursor (GitHub keeps its comment there). `identity_key` = `gitlab-mr-note:<provider>:<path>:<iid>:<project>`, without the action: the job reconciles when it runs — the preview open and `deployed` gets the «ready» note, no preview and a job queued for a failure or a fork gets that note, anything else (closed, gone) loses it. The close's job has a key of its own, ending `:closed` (10-nov-2026): collapsed into a job waiting for its retry, it ran with that job's arguments, and a failure's note was written again on a closed merge request. A failure's or a fork's job also deletes instead when a `close` of the merge request was processed after the delivery that queued it (`event_id`). The note is found again by `pr_comment_id`, else by the marker `<!-- incubacloud:preview:<panel>:<project>:<iid> -->`, `<panel>` the first 12 hex characters of the SHA-256 of `database.uuid` so two panels on one merge request never take each other's note, among the notes of the credential's `token_user`, read 100 at a time, oldest first, up to 10 pages (`MAX_NOTE_PAGES`): a repeated job rewrites, never writes twice; a 404 on delete is done. The project's name and the reason in a failure's note are put on one line without backticks: a line break could start a GitLab quick action. One run spends at most `NOTE_BUDGET_S` = 60 s on GitLab (`GitLabClient(deadline=…)`), so a slow server does not hold a queue_job worker for minutes. It needs a credential with `api` for the path; without one (`no_notes`) the job only logs. Retries (10-nov-2026): GitLab unreachable, timing out, 5xx or 429 is retried after 60, 300 and 900 s (`RETRY_SECONDS`, about 20 minutes in all: a short GitLab outage leaves no preview without its note, more adds nothing); then, or at once on a refusal (401, 403, 400, 422, a server the network policy refuses), `pr_preview_note_failed` goes on the production a failure is about, else the preview, else the merge request (`gitlab_mr:<provider>:<path>:<iid>`). A note that goes through resolves it on all three, and the close resolves the merge request's. A note that could not be deleted only goes to the log: the merge request is closed, nothing would resolve it. The preview works without its note.
- **Values (8-nov-2026).** Body 8 MB (GitLab caps a push at 20 commits); one test per webhook every 15 s (GitLab allows 5 a minute); orphan webhooks deleted after 7 days; events kept 30 days (`gitlab_event_retention_days`); 3 dispatch attempts. Measured from GitLab (CE 19.5.3 and gitlab.com 19.6.0-pre): 10 s delivery timeout, no retries of its own, gitlab.com disables a webhook for a minute and growing up to a day at the 4th failure in a row and for good at the 40th, CE only with `auto_disabling_web_hooks`; a 2xx test re-enables it, a `PUT` does not; a `PUT` without `token` wipes the secret, so the panel always sends both.

## Staging autopurge

Once a staging stops counting against an allowance, nothing pushes anyone to delete one, and they are not free: disk on the customer's host, probes and series in the central stack, and a copy of production data nobody remembers is there. A staging unused for `cloud.settings.staging_autopurge_days` (default 90, `0` disables, floor of 28 so the warnings still land in time) is deleted. Production is never a candidate, nor is an archived instance, nor one flagged `autopurge_exempt`.

**The clock is two fields and the later one wins** (`cloud.instance._autopurge_clock`). Both are fields of their own and never `write_date`, which the daily crons would push forward forever — the same trap `archived_at` documents.

- `last_touched_at` — somebody acted from the panel. Sealed on `create()` (so no row is ever clockless, including copies, since `copy=False` drops it), by `queue_job_ext.QueueJob._seal_autopurge_clock` when a **visible** job authored by a **human internal user** reaches `done` (the seal runs after the job commits, on a cursor of its own: the job's hooks commit writes on the same row, so an UPDATE inside the job's transaction loses the serialization race and queue_job re-runs the whole job), and by the connect-as and terminal-open controllers, neither of which leaves a job behind. Hidden types (the probes) and anything the bot starts on its own — a rebuild off a push above all — are excluded by design: either counting would keep every staging alive forever and leave the feature dead code that looks alive. `create_uid` is trustworthy here precisely because everything the platform starts goes through `as_platform`.
- `last_login_seen_at` — the last login inside the staging's own database, read daily by the hidden `read_last_login` job (`cron_read_staging_logins`, running and non-exempt stagings only). The script picks `res_users_log` or `res_users.login_date` by asking the database with `to_regclass`, not by trusting the panel's `odoo_version`. **A failed reading writes nothing**: a stopped container, an unreachable database or a garbled answer must never be recorded as "nobody logged in". The value is also monotonic — an older answer (a restore from an old backup) and a future one (a skewed host clock) are both refused.

**The ladder** (`_cron_autopurge_stagings` → `_autopurge_step`, daily) climbs **one rung per tick**, and each rung requires the one below it: first warning at `AUTOPURGE_WARN_DAYS` (14) out, final warning at `AUTOPURGE_FINAL_DAYS` (3), deletion at the deadline **and** at least 24 h after the final warning was stamped. That ordering is the whole design: the naive version — evaluate every condition, act on all that match — warns twice and deletes in one sub-second pass when the cron comes back from an outage, which is notice in form and nothing in substance. Failures are reported and skipped per instance, so one unreachable host does not keep the rest alive.

Two alert codes (`staging_expiring` warning, `staging_expiring_final` critical) rather than one that escalates, because `cloud.alert` only dispatches notifications on **create**: re-raising the same row at a higher level reaches nobody, and `critical` is the only level the default `failures` preference delivers. Both are resolved by `_touch_autopurge_clock()`, which also clears the two warning stamps — an instance that comes back to life gets its whole notice period again, never "three days left and no warning showing".

Deletion goes through the ordinary path (`delete_instance` enqueued `as_platform` when deployed, `unlink()` when not) — the same one a closing pull request uses; a second way to delete an instance is a second way to get deletion wrong. An audit row carrying the instance **name** is written first, because `cloud.audit.log.instance_id` is `ondelete='set null'`. A busy instance no longer refuses it: the delete cancels what waits in its queue and waits for the job running. An enqueue refused anyway (a delete already waiting, a failure) raises `staging_autopurge_stuck` and retries tomorrow.

`_autopurge_days_left()` answers only once the first warning is out — a countdown on every staging from birth is something people learn to scroll past — and travels through `/cloud/get_instance` and the project instance list. `/cloud/keep_instance` (consultant-gated, the same role that can deploy) is the one-click reset, audited.

## Egress on staging (the "Whitelist" tab)

A staging is a copy of production that people poke at, so what it can reach matters. Until template v9.6.0 the answer was decided per *host*: `cloud.host.whitelist` builds one `docker-whitelist` proxy per hostname in `~/globalwhitelist`, and every test instance on the machine joins the same network by alias. That answers "what may stagings on this box reach", which is not the question a customer asks — theirs is "this staging has to reach *their* API".

`cloud.instance.whitelist` is the per-instance answer. It travels as the `whitelisted_hosts_test` copier answer, so it is part of the config snapshot: saving lights the drift pill and it applies on the next rebuild. A new staging is seeded from its host's list, and production is never filtered by us — its answer is always `[]`. What the template renders from that answer depends on its version, and **a stack keeps the model of the template that rendered it until it is rebuilt**: the panel records that template on the instance (`stack_template_ref`, written by deploy and rebuild; empty for a stack rendered before it existed, which is the old model) and reads the stack from it — `expected_services()`, the health probe, where the deploy puts its Traefik labels.

*Template v9.6 to v9.x:* a non-empty list renders a NAT gateway (`proxy_general`) plus a sidecar (`odoo_net_setup`) that shares the odoo container's network namespace and replaces its default route; an empty list falls back to the host's shared proxies, which the template joins either way.

*Template v10 (the pin since core 1.0.195):* one `gatekeeper` service owns the network namespace `odoo` runs in (`network_mode: service:gatekeeper`), filters with nftables (reject by default; the allowed set is resolved from `ALLOWED_HOSTS` every `REFRESH_INTERVAL`; private ranges and the two upstream resolvers always pass) and carries the staging's Traefik labels, the login routers among them. It fails closed: without the gatekeeper odoo has no network at all, and `odoo` waits for its healthcheck (`condition: service_healthy`) to start. The shared whitelist network is gone, so an empty list of the staging's own would mean no egress at all; the panel keeps the old meaning by rendering the host's list instead (`_egress_whitelist`). The override pins the image by digest (`GATEKEEPER_IMAGE`: upstream publishes `latest` and pull-request tags only) and gives it the restart policy the template does not, so a host reboot brings the staging back (`_gatekeeper_override`). The gatekeeper gets a new namespace every time it starts, and a running odoo stays in the old one, which keeps no route out (Traefik, which reaches odoo through the gatekeeper, answers 502): after an `up`, `start` or `restart`, `compose_op.sh` reads odoo's routes and restarts `odoo` when it has none, so odoo joins the namespace the gatekeeper has now; a restart of the whole stack is a `stop` and a `start`, in dependency order, waiting for what odoo depends on to be healthy. When the script cannot read what a step after the operation needs — the compose, what runs, odoo's routes (30 seconds at most) — the operation has still run: it names the step it could not check and what may be wrong, and exits 24 (`COMPOSE_OP_EXIT_UNCHECKED`) instead of 0. The start, restart, restore and backup restore jobs take 24 for their step done: they succeed, with a warning in the job log, and everything a success brings runs as usual. What may be left wrong is the health probe's to see: for a stack with a gatekeeper it reads the same routes, and odoo without one, or with its gatekeeper not running, counts as Odoo not answering (`instance_unresponsive`, critical, on the second probe in a row, with the cause and "Restart the instance"); routes it could not read change nothing. It also grades an unhealthy gatekeeper as `instance_egress_filter_lost`: nothing opens up, but the staging reaches nothing it is allowed to.

**Two of the old template's choices are not ours to ship, and the deploy override undoes both** (`_net_setup_override`, for stacks still on that model).

*The host's docker socket.* `test.yaml.jinja` mounts `/var/run/docker.sock` into the sidecar unconditionally — no copier question turns it off. It is read by exactly one function of the image's entrypoint, guarded by `DNS_INTERNAL_FROM_DOCKER`, whose default *in the script* is `0`; the template is what turns it on. The work that matters — resolve the gateway, pick the interface, `ip route replace default` — never touches Docker, and the internal DNS that function builds is already served by Docker's own resolver at `127.0.0.11`, which the sidecar's dnsmasq forwards to and which answers service names and network aliases alike. Measured on this panel's own devel, which has run with the lookup off and no socket for months: `/run/dnsmasq-internal.hosts` is empty, `db`/`smtp`/`wdb` and the network aliases all resolve, the default route points at the gateway, and a host outside the list still gets nothing.

So the mount buys nothing and costs everything. `:ro` marks the *mount*, not the protocol: talking to a unix socket is `connect()` plus `send()`, and the Docker API has no read-only mode — the same channel accepts `POST /containers/create` with a bind of `/` and `privileged`. On a host shared between customers that is not "can see other containers", it is root over the machine and everyone on it. The override re-points the target at `/dev/null`, because **an empty `volumes:` list does not remove a mount**: compose merges volumes by target path, so the base file's entry survives it.

*A disabled healthcheck.* The template ships `healthcheck: disable: true`, while the route injection happens once, at start. Restart the odoo container and Docker hands it a fresh netns with the default NAT route: the injection is gone, the staging has free egress, and the sidecar stays `Up` because its last line is `tail -f /dev/null`. Every light green. That is the 2026-08-06 incident on this panel — three and a half hours sending Telegram to the live channel — which is why `devel.yaml` has carried a route check ever since. The override ships the same check (pure shell: the image has `/sbin/ip` and little else, and a lost injection is recognised by the default gateway's last octet being Docker's own `.1`), and `disable: false` is said out loud because compose merges the healthcheck mapping key by key.

`expected_services()` names both sidecars whenever the list is non-empty, which is the same condition the template renders them on. That is what gets them probed, labelled against the daily `docker system prune`, and log-rotated; they get no resource limits, because two shell scripts and a dnsmasq are not a number this module should invent.

**Which containers a user may sit inside is a server-side list.** `terminal_open` used to validate the *shape* of a service name and open whatever matched, so the browser's selector was the gate. `cloud.instance._shell_services()` now answers it — `odoo`, `db`, `smtp`, `backup`, intersected with what the last deploy actually found — and the route refuses everything else. An allow-list, not a deny-list: a service the template grows next year is excluded until somebody says otherwise.

## Captured mail on staging (the "Mails" tab)

Every staging renders a MailHog container and the doodba template wires Odoo to it (`SMTP_SERVER: smtplocal`), so a copy of production never mails real customers. That has always been true and was never visible. `controllers/_data_load/_mailbox.py` builds the three commands that make it readable; `_routes_ops` exposes them at `/cloud/instance_mailbox`, `/cloud/instance_mail` and `/cloud/instance_mailbox_clear`.

**The catcher is only reachable from inside the stack**, which is the point: core 1.0.128 took away its Traefik router, because the template publishes the inbox at `/<domain>/smtpfake/` with no authentication and `cidr_whitelist` is `null` on our deploys. So the request is issued with `curl` from the instance's own `odoo` container, which is on the compose network and already carries `curl` (the health probe uses it). Taking the container off Traefik also hides the middlewares the template declares on it — the ones the staging's Odoo routes use — so the override declares the same five (`addSTS`, `buffering`, `compress`, `forbid-crawlers`, `forceSecure`) on `odoo`; without them every staging answered `404 page not found` (fixed in 1.0.151).

**The projection runs on the host, not in the container.** A staging can be any Odoo from 7.0 up, so its container's Python is whatever that era shipped — the trap `read_last_login.sh` had to dodge. The host is ours and has python3, so `docker compose exec … curl | python3 -c "$PROG"` puts the parser on the right of the pipe, in the SSH shell. Two consequences: nothing is assumed about the instance's image, and only the projected JSON crosses SSH — a mailbox of fifty messages with attachments is megabytes, none of which the panel would show.

Bodies are rebuilt from MailHog's `Raw.Data` with Python's `email` package rather than from its own `MIME.Parts`, because the raw message is the only representation carrying each part's charset and transfer encoding — which is what turns a quoted-printable `=C3=B1` back into an `ñ`, and an RFC 2047 `=?utf-8?q?…?=` subject into something a person can read. Attachments are listed (name, type, size) and never carried. The listing, the message and the attachment list are all bounded (100 messages, 256 KB of HTML, 64 KB of text, 50 attachments), and a truncated body says so.

Gated on `can_view_logs` (developer+): the same data class as the logs, read the same way, and capped per user by its own `rate_limit_mail_reads_per_min` because a mail read costs a `docker compose exec` plus an HTTP call inside the stack where a log read is a `tail`. Nothing is stored in the panel. Production has no catcher, so the tab is absent rather than empty, and the four ways to have no mailbox — production, not deployed, stopped, gone — each answer in their own words: an operator who cannot tell them apart concludes the feature is broken. Clearing is audited; reading is not, matching the proxy access log.

In the browser the HTML body renders in an `iframe` with an empty `sandbox`, so no scripts and no same-origin: it is mail generated by somebody else's database.

## A production's mail relay (1.0.224, 10-nov-2026)

A production with `smtp_relay_host` runs the template's `smtp` service, a docker-mailserver relay (`SMTP_RELAY_IMAGE`) Odoo sends to. `smtp_relay_auth` says how the relay signs in to its server:

- **`password`** (the default): `RELAY_USER` and `RELAY_PASSWORD` from the copier answers, as always.
- **`oauth2_microsoft`**: Microsoft 365 with the client credentials of an app in Entra ID. Production only (`_check_smtp_relay_oauth`); the server is fixed to `smtp.office365.com:587` STARTTLS (`_relay_oauth.MICROSOFT_SMTP_SERVER`, written by `_relay_server_vals`), `smtp_relay_user` is the sender mailbox, and the directory ID, the application ID and the client secret (`EncryptedChar`, Developer, in `_PASSWORD_FIELDS`, not in `_SECRET_FIELDS`) are required. The answers keep their keys: `smtp_relay_password` is the path of the token file (`/var/lib/ic-relay-oauth/token.json`), which sasl-xoauth2 reads as its "password". `_extra_env_files` writes the credentials to `.docker/smtp-oauth.json` (0600); the override runs `RELAY_OAUTH_IMAGE` (by digest, built on `SMTP_RELAY_IMAGE`'s release, `images/relay-oauth`, RB-31), mounts the file read-only at `/run/secrets/ic-relay-oauth.json` and labels the service with a fingerprint of the credentials, so `up` recreates it when they change (a bind-mounted file's content is not part of a container's configuration). Without OAuth2, deploy and rebuild remove the file (`_relay_oauth_file_step`); with it, they remove a directory Docker may have left at its path. The snapshot carries `smtp_relay_oauth` (provider, both IDs and the secret's fingerprint salted with the instance's id) only for an OAuth2 relay, so the rest of the fleet keeps its hash.

**Whether it delivers.** The health probe's step `relay_delivery` reads, inside `smtp`, the renewer's state (`ic-relay-oauth status`), the deferred mail of `postqueue -j` (age and reasons, addresses removed), the time of the last `status=sent` to the relay host in `mail.log` and `maximal_queue_lifetime`. `_grade_relay` raises `smtp_relay_failing` (critical, confirmed over two probes by `cloud.alert.policy`) for a deferral `_relay_oauth.classify_reason` names (connection, DNS, TLS, credentials or token refused, SMTP AUTH disabled, Send As, the hop to Amavis on `127.0.0.1`) in a message older than `RETRIED_SECONDS` (660 s, past Postfix's next try, so one deferral seen by two probes is not counted), a mail deferred longer than `STUCK_MINUTES` (30) for any other reason, or an OAuth2 token that is running out while the renewer fails (`token_failure`). A recipient refused (`in reply to RCPT TO command`) is not one, and the reducer drops those before keeping the twenty oldest messages. Only a delivery resolves it: a `status=sent` later than the alert's `last_raised_at` (the last failure seen), or the test mail. A token `ok` and an empty queue do not, since Exchange refusing a good token gives both. Changing the relay's host or authentication resolves it and resets `smtp_relay_state`.

**The test mail.** `send_relay_test_mail` (route `/cloud/instance_relay_test_mail`, MCP `send_relay_test_mail`) holds every check: the consultant role, the instance as the caller reads it, `_relay_test_refusal` (a stopped or sleeping instance included) and then five an hour per instance (`RELAY_TEST_MAILS_PER_HOUR`), so a refused test costs nothing. It queues `relay_test_mail` (`queue_exclusive`, `failure_holds_queue` False, no retry) with `sudo`: the type is a manager's in `_job_type_min_group`, so it is never queued directly below that. The executor sends to the job's creator (`create_uid.email`, checked with `valid_mailbox`) with a tag of its own, never to an address in the payload; a retry goes to whoever retries. `scripts/relay_test.sh` sends it with swaks on the relay's port 25, follows it by its Message-Id through Amavis (which queues it again under another ID) to the relay's verdict, removes it from the queue unless it was sent (a `HUP` or `TERM` trap does the same when the job is cancelled while it waits) and flushes the queue when it was. The job ends `done` with `delivered` and the server's answer; a deferral of no known cause gives no verdict, as a timeout, and leaves it to the probe; a refusal for a cause of the relay's raises the alert at once and drops the probe's suspicion, so the probe updates that alert instead of confirming another.

## Alerts and notifications

### Alerts

`cloud.alert` rows target a host, instance or project (or none = global) with a machine `code`, a `warning`/`critical` level and an `active`/`dismissed` state. **Every producer goes through `raise_alert`/`resolve_alert`**; none creates a row by hand. One active alert per identity: (code, instance, key) for an alert about an instance — the host given with it only says where it runs, so the alert stays the same when the instance moves —, (code, host, key) for one about a host, and the project too for one about a whole project. The `dedup_key` tells apart what the target alone does not: `backup_backend:<id>` for a backend's alerts, `job_type:<code>` for `job_failed`, `project:<id>` for a project's; a module built on top may add its own. Creators re-use the existing row, and a partial unique index (`cloud_alert_active_identity_uidx`) enforces it against two producers racing under snapshot isolation — the loser's insert is refused and treated as success. `job_failed` is exempt from the index; a repeat failure of the same type and target refreshes the open alert and bumps its `occurrences` instead of stacking a row per attempt. Health and metrics executors **auto-resolve** their alerts when the condition clears, and a job success dismisses stale `job_failed` alerts for the same type and target. Dismissed alerts are garbage-collected after 60 days (cron); active ones never expire.

**A measurement confirms itself first.** `cloud.alert.policy` holds, per alert code (or per family, `instance_service_*_down`), how many sightings in a row make the condition an alert and how fresh each must be; `raise_alert` reads it for every caller that brings no count of its own, keeps the first sightings as a `cloud.alert.suspicion` (one row per code and target, its own unique index, never listed, counted or notified) and only raises on the N-th sighting in a row, each within the window of the last; a clear reading or `resolve_alert` forgets the suspicion, and the alert GC drops suspicions nobody refreshed for a day. The shipped rows (`data/alert_policy_data.xml`, not `noupdate`) are the metrics backend, `instance_down`, the companion containers and the SSH disk probe, all at two sightings within three ticks; a layer may add rows of its own. The producers that measure raise their code and nothing else. A code with no row is an event (`job_failed`, `host_key_changed`, …) and raises on the spot. Metric rules are the one caller that passes its own count: `confirm_cycles` per rule (default 2; 1 for expressions that already measure over a window), because their codes are the operator's. A document read once a day (such as a provider's published address ranges) has no next tick to confirm on and reads twice within the pass instead. The older per-instance `*_streak` fields of the SSH health probe predate all this and still do their own counting for CPU, memory and HTTP.

**Audience.** `cloud.alert.audience` is `fleet` (default: whoever runs this panel's hosts, instances and repositories) or `provider` (whoever runs a service the panel depends on but does not own: the metrics central when `metrics_central_host_id` is empty, an undecryptable secret, an instance record left behind, a prune that swept managed containers). `_dispatch_notifications` and `_notify_alert_resolved` ask `_route_provider_alert(resolved=)` before paging anyone about a provider alert; core's default returns False, so a self-hosted operator — who is the provider — is notified as usual. The bus broadcast is never skipped: the panel shows the alert either way. A layer whose panels run under a provider may override the hook to relay the alert to that provider, mark what it relays `for_provider` and hide it from the panel's users with a global record rule on that field. The field is core's, and core never sets it: such a rule is in the panel's database while core loads alone (its at_install tests, a migration or a `<function>` that raises an alert), and a rule on a field core lacked failed every read of every alert there (27-oct-2026).

**Silent codes.** `_silent_alert_codes()` names the alerts a panel lists but tells nobody about: `_alert_user_eligible` (mail, Telegram and webhook, at an alert's opening, its turning critical and its resolution) and the daily digest leave them out; the Alerts list, the bell's count and the bus do not. Core's answer is empty; a layer adds the codes that are only informative on its panels, such as `host_hardening_outdated` where the panel's users cannot act on it.

**Provider alerts are inventoried.** `cloud_alert.PROVIDER_ALERT_CODES` lists every code core raises with `audience='provider'`; `test_provider_alert_inventory` reads the source (every call or dict that can set the audience to `'provider'`, conditionally or not) and fails on one missing from the list or listed but no longer raised. `encrypted_value_unreadable` reached customers' panels before anybody knew it was one (18-oct-2026).

Alert codes in use: `secret_key_not_escrowed`, `job_failed`, `disk_critical`, `host_unreachable`, `instance_down`, `instance_unresponsive`, `instance_high_cpu`, `instance_high_memory`, `instance_memory_recycling`, per-service container-down codes, `instance_error_logs`, `pip_conflict`, `addon_conflict`, `move_stuck`, `secret_rotation_stranded:<field>`. `pip_conflict`/`addon_conflict` are *actionable*: they block re-enqueue of the affected operation and are excluded from bulk dismiss.

### Notification channels

All channels share one recipient rule: **active internal users filtered by record-rule visibility** and their own preferences (level `all`/`failures`/`none`, muted projects). Two paths feed them:

- **Alert pipeline (unified)** — every `cloud.alert` creation calls `_dispatch_notifications()`, which fans out to email, Telegram and webhook. Job **failures** create a `job_failed` alert and are notified through this path — there is a single code path for infrastructure alerts and failed jobs.
- **Job path** — successful job completion (`done`) is notified directly from the `queue.job` state bridge (no alert is created for successes).

| Channel | Enabled by | Notes |
|---|---|---|
| Bus (real-time) | always | `cloud_jobs` (job events → toasts) and `cloud_overview` (alert badge + critical alert toasts) |
| Email | per-user toggle | Immediate or **daily digest** (07:00 cron, QWeb template, watermark per user). Critical alerts and severe failures bypass digest mode. |
| Telegram | bot token + chat id set | Markdown message via the Bot API, every name and message in it escaped as text (`telegram_markdown`); chat-id auto-detect and test-message endpoints in the UI |
| Webhook (HMAC) | HTTPS URL set | JSON POST per event, optionally signed |

For users at level `failures`, the alert pipeline only delivers `job_failed` alerts and critical alerts.

Webhook payloads — two event types:

```json
{"event": "job_state_change", "job_id": 123, "job_name": "Deploy Instance",
 "state": "done", "severe": false, "host": "host-1", "instance": "prod",
 "log_url": "https://…/cloud/log/123", "timestamp": "2026-07-12 10:00:00"}
```

```json
{"event": "alert", "alert_id": 45, "code": "job_failed", "level": "critical",
 "message": "Deploy Instance on prod failed", "host": "host-1",
 "instance": "prod", "job_id": 123, "log_url": "https://…/cloud/log/123",
 "timestamp": "2026-07-12 10:00:00"}
```

When a secret is configured the request carries `X-IncubaCloud-Signature: sha256=<hex>` — HMAC-SHA256 of the raw body — on both event types. Verify with a constant-time compare. No secret → no header.

A separate email alert covers **backup bucket usage** (quota threshold per backend, 7-day debounce), outside the alert panel.

## Extending an instance's stack (addon hooks)

Deploy and rebuild render the whole stack in `DeployInstanceExecutor` and its subclasses. An addon adds to it through `cloud.instance` hooks instead of patching executors; each answers "nothing" in core, so an instance without such an addon is rendered exactly as before:

- `_extra_services()` — compose services the addon adds. Listed in `expected_services()`: they get the platform's protect label and log rotation, start with the stack and are watched by the health probe. Each must be defined by a fragment (with its `image`).
- `_compose_override_fragments()` — `{service: {key: value}}` merged into `docker-compose.override.yml` and never over it: mappings gain keys the platform did not set, `volumes`/`env_file`/`depends_on` gain entries, any other key is set only when absent (a fragment cannot replace Odoo's `command` or a limit).
- `_extra_env_files()` — files shipped into the instance directory on every build, staged 0600 and moved into place 0600 before the stack starts ("Write extra env files"). A file an addon stops listing stays until the addon removes it.
- `_teardown_pre_steps(dir, keep_in_panel)` — steps run before a delete tears the stack down; never on a move's cleanup of the copy it left (the instance lives on).
- `_after_stack_rendered()` — called by deploy and rebuild success: what the hooks answered is now on the host and running.
- `_after_restore_hook(kind)` — called once the database was replaced: `restore` (a copy restored onto it), `backup_restore` (one of its own backups, a revival included), `move` (its cutover, after the restore on the target), `pitr` (its own database brought back to a moment by `incubacloud_pitr`, also when its files could not be).

`cloud.job._get_health_blocking_job_types()` lets an addon whose jobs restart containers on purpose keep the health probe from reporting them, without overriding the probe. `cloud.job._get_health_blocking_host_job_types()` does the same for host jobs that stop the instances of their host: while one runs, those instances' probes skip their pass, and leave their streaks and alerts as they were — the job changes nothing in them, where a job of the instance's own resets both. After either kind has ended, the probe's error window opens one minute after its `date_done`, so the connections it cut are not read as errors.

## Continuous recovery (`incubacloud_pitr`)

A separate module, off until switched on per production instance (managers; a staging never archives). Once on, the instance's database hands its write-ahead log to its own backup bucket and its filestore is copied as it changes, so it can be restored to **any minute** of its backup window (its backend's retention, or the one a layer on top sets). The recovery objective — the most it may lose — is 1, 5, 15 or 60 minutes.

- **The credentials never reach the database's container.** Odoo connects as a superuser, and a superuser's SQL can read that container's environment (`COPY … FROM PROGRAM`): an addon of the instance's would hold the bucket's key, which often opens every instance's backups. They live in one container, the **`pitr` agent** (rclone image, by digest), with `.docker/pitr.env` (0600). `db` only mounts `.walg/` read-only, and its `archive_command` is `/opt/walg/archive %f`, a script that holds nothing secret: it waits, up to a minute, for the mark `spool/done/<segment>` the agent leaves once it uploaded that segment, and fails otherwise (PostgreSQL keeps the segment, retries and counts the failure).
- **The agent** sees the data directory read-only. Every second it uploads, in order, the segments PostgreSQL marked ready (`pg_wal/archive_status/*.ready`), each under **its cluster's** prefix (`<prefix>/<system identifier>`, read from `pg_control`): a move or a new deploy initialises a new cluster, whose segment names would otherwise land on the old one's, and the prefix follows a change of backend with the next rebuild. Every objective it copies the filestore's files changed since the last copy that worked (`--max-age`, no listing of the bucket; `spool/fs-ok` records when it started); once a day an exact copy, whose deletions are moved to `deleted/<day>` so a restore to before them brings them back. Encrypted (rclone crypt, a password derived from `pitr_key`). It runs the base copies too, connecting to `db` with Odoo's password.
- **wal-g**, pinned (`_constants.WALG_VERSION`, sha256 checked on the host, a download file of its own per install), compresses (brotli) and encrypts (libsodium, with `cloud.instance.pitr_key`, born with the instance; a neutralized copy gets a new one when switched on) before uploading. Its builds are for glibc and the images are Alpine: `pitr.sh install` copies the host's glibc loader and the four libraries wal-g needs into `.walg/` and runs it through them (`--argv0`, so the copies of itself wal-g starts go through the same wrapper).
- **Archiving**: a stack rendered with the module starts `db` with `-c archive_mode=on` (the one setting only a restart changes; `CONF_EXTRA` would be replaced by the override), so switching on is a reload and no database restarts under a customer opening an instance just announced ready. Until then it has no archive command and keeps its segments, which `pitr_enable`, queued as the stack is rendered, follows within minutes. Its first step settles that (`pitr.sh settle`, no network): only an archive of the cluster the panel has base copies of, archiving with `/opt/walg/archive %f`, is kept; anything else — no command, `/bin/true`, any other — gets `archive_command = '/bin/true'` and a reload (never a restart), and the segments go: without a base copy before them they restore nothing. A switch on that fails or is stopped before archiving works asks the host to settle again (`on_failure`, a connection of its own, after the stop's TERM wait): `parked` is `off` with a warning and the retry in a day, `kept` leaves the archiving it had (`failed` when this switch rewrote the command and the upload test failed, critical), no answer is critical, even for a cancelled job. `settle` leaves the agent alone: a switch on whose TERM did not reach root may still write the real command. Its failure holds no queue (`failure_holds_queue` off, 8-nov-2026): the retry its alert promises, the base copies and the backups are not stopped behind it. Not covered: a rebuild of the chain that fails after starting `db`, or a `pitr_enable` cancelled while it waits, runs no hook of this module; the rebuild's failure holds the queue and the database keeps its segments until someone acts (a follow-up would park it from `_cron_pitr_watch`). Everything is also written with `ALTER SYSTEM` (`postgresql.auto.conf` lives in the data volume and survives recreations): `archive_command`, `archive_timeout` = the objective, and `archive_mode` itself, since a restore's recovery starts the data directory without the stack's command line and must archive the timeline it begins; a database not archiving yet (a stack rendered before) is restarted once, Odoo stopped around it and started again however it ends. Switching on checks one segment end to end. Switching off starts a stopped database to drop the settings (left there, its next start would archive to a command the rebuild removes and keep every segment), and first of all sets the archive command to `/bin/true` with a reload, wherever `archive_mode` comes from: a cut anywhere after it, or a rebuild that drops the mount before the rest, leaves the segments let go. While the flag still holds archiving on, until the rebuild that follows drops it, nothing restarts; with `archive_mode` from `postgresql.auto.conf` the database restarts once, Odoo around it.
- **Base copies**: the first of a cluster is full; then daily (an hour per instance, 01–05 UTC), delta, and full again whenever the newest copy is of another timeline — wal-g would otherwise build a delta on a copy taken before a restore to the past, which holds changes the restored database never had. Then housekeeping, each part on its own: what leaves the window (`delete before FIND_FULL`, so a kept delta keeps its full copy), old filestore deletions, a previous cluster's archive once out of the window (never the current one). A base copy whose housekeeping failed is still recorded.
- **Watch**: every ten minutes, for running instances not moving, one policy (`_pitr_reconcile`, also called after a rebuild) switches on what is wanted and off what is not, never again within a day of a switch that failed; and `pitr_status` reads `pg_stat_archiver`, the segments waiting in `pg_wal/archive_status` (none waiting means nothing is owed, however long ago the last left: an idle database is not behind), whether the agent runs, and `fs-ok`. Archiving off or a new cluster → switched on again; failures or the agent down → `pitr_failing` (critical); the log or the files behind by more than three objectives → `pitr_archive_lagging`; no base copy, or none for 36 h → `pitr_base_missing`.
- **Restore to a moment** (`pitr_restore`, after a duplicity snapshot of the present when the instance has one). The base copy is chosen by the panel (`choose_base`): each restore starts a new timeline at its promotion, branching off the moment it went back to (`pitr_timelines`); the copy must have been taken before the moment on the timeline live at that moment, or serve the moment that timeline branched off — a copy taken after the branch on the old timeline holds a history that was abandoned. The restore itself runs on the host, **detached** (`pitr.sh restore-start` hands it to a process of its own, holding `.walg/restore/lock`): Odoo stops, what the database still holds is archived, the copy is fetched **beside** the current data (wal-g only fetches into an empty directory) with room checked against the data as it is, swapped in, and recovered in a database container of its own that has the credentials `wal-fetch` needs — the `db` service never does, and nothing of the instance's runs meanwhile. That container's server runs with the panel's own restore and archive commands and ignores the server settings stored inside the restored copy, and so do the restore's connections to it. If it does not come up, or the process is interrupted before it did, the previous data is put back; however it ends, the instance is started again and `.walg/restore/result` says how. The job follows it for 50 minutes and hands it to a job of the same type (`follow`) while it runs; the same job run again follows its restore instead of starting a second one. Then the filestore, a record of the new timeline and a full base copy of it.
- **Cancelling a restore** (6-nov-2026: a cancel used to stop the following only, and the restore went on unseen). Cancelling is stopping and undoing. `on_cancelled_running` opens a connection of its own (the run's is closed) and runs `pitr.sh restore-cancel <job> <wait>`: it writes `.walg/restore/cancel`, sends a TERM to the restore's process alone, and waits for its `result`. Up to the promotion, the process stops the phase it is in and puts the previous data back (`finish`/`rollback`); `result` says `cancelled=1`. bash runs a trap only once the command in the foreground ends, so the long steps run **in the background with a `wait`**, which a TERM cuts short: the drain, and the fetch, now in a container of its own (`pitr-fetch-<job>`) that only writes `.pitr-new`; `finish` removes the containers, then takes the step's whole process group down (the drain's `docker compose exec`), up to 10 s, before `docker compose up -d`. The swap only renames and runs in the foreground: a cancel waits for it and never finds it half done; `rollback` drops `.pitr-new` when nothing was moved. Once the restored database is promoted a cancel undoes nothing: the restore goes on to the end, filestore included (`done`, or `db-only`), rather than leave files half restored behind a database that replaced the previous one. A cancel and a start never cross: the start writes its lock and then reads `cancel`, the cancel the other way round; the process writes `armed` once its traps are set, and the cancel waits up to 10 s for it before its TERM. `restore-cancel` answers `none` (and `held_by=<job>` when another job's restore holds the instance) when nothing of the job started, `running` when the wait ended first, `lost` for its own lock with no process. The job: put back → confirmed running, no alert; `none` → nothing; `done`/`db-only` → recorded as a restore (`db-only` critical); `failed-unknown` and `lost` → critical, with where the data is (`.pre-pitr-*`, `.pitr-failed-*`); `running`, no answer or no connection → the next job follows it (`_follow_on`, critical when the host was not reached). A job following a cancelled restore reads `cancelled=1`: undone with no alert, or «already applied». Alerts are raised again (`ic_job_cancelled=False`). The queue stays held while the hook waits: `_scope_busy` counts a cancelled job whose `queue.job` runs, and the hook runs in that `queue.job` (`_dispatch_cancel`).
  - **How long the hook waits.** In the job's own run, 300 s on the host (`CANCEL_WAIT_S`, SSH timeout 300 + 120): a phase stops in seconds and a rollback only renames. Outside it — the reconciliation of lost jobs, and a job stopped before its attempt began (`_close_stopped_before_run`) — 30 s (`CANCEL_WAIT_OUTSIDE_RUN_S`), then the next job follows it: the reconciliation runs in the cron thread every other cron waits for (the runner has one, `--max-cron-threads=1`) and starts no other clean-up once a pass took 60 s (`_RECONCILE_HOOK_BUDGET_S`). Its first clean-up always runs, so a PITR cancel there holds the pass for about a minute (30 s, the connection, the upload, up to 10 s for `armed`), and the rest of the batch goes to the next pass five minutes later; the 300 s there would have held every cron of the panel up to seven minutes. `on_abort` there asks once, with a 120 s cap.
  - **What it leaves.** A stop whose worker died for good is closed by the reconciliation with its `queue.job` failed: the queue is no longer held from then, and while the host still undoes a rebuild queued on the instance could start beside it. The host's lock refuses a second restore, a rebuild does not read it; the hook's `_follow_on`, when the undo outlived its 30 s, holds the queue again. A host that never answers is followed eight times (`RESTORE_UNREACHABLE_MAX`) and then given up with its alert. Not handled in this change.
- **Its pieces reach the stack through the hooks above**: the mount on `db`, the `pitr` service, `.docker/pitr.env` (kept while the instance has an archive, so a delete purges it with fresh credentials), and the README files that create `.walg/` and its spool as the host user. Switching on is a rebuild then `pitr_enable`; a setting applied by a rebuild switches it with `_after_stack_rendered`, without a second one. Deleting the instance purges its prefix (`<folder>/<name>-pitr`, beside the duplicity prefix, never under it), once with the stack up and once more after the agent and the database stopped.
- `pitr_*` fields are written by managers or by the panel itself only (`write` refuses others): switching the archive off, or pointing it at the wrong cluster to purge, loses a customer's history. `pitr_stack_external`: a stack whose compose is not the panel's (the platform's own manager): the panel only watches it and takes its base copies; switching and restoring go through its runbook (`invoke pitr-manager`). Uninstalling the module is refused while an instance archives.

## Agents (MCP, `incubacloud_mcp`)

A separate module: `POST /mcp` lets AI agents operate the panel as the user who connected them. Full reference in [`mcp.md`](mcp.md); user guide in `docs/user/docs/agents/`.

- **Authentication.** `Authorization: Bearer` only, never the cookie: an RS256 `at+jwt` of the configured issuer whose audience is this panel's canonical `/mcp` URL (keys found through the issuer's metadata, cached), or an Odoo API key where the panel allows them. The request then runs as that user (`request.update_env`), never as the superuser.
- **Protocol.** 2026-07-28 statelessly; 2025-03-26 to 2025-11-25 through `initialize` and a session id the server signs and does not store.
- **Dispatch.** Each tool resolves its route in `ir.http.routing_map()` and calls the final endpoint inside a savepoint: the panel's own role checks, record rules and the overrides of modules on top apply. Tools and route policies form a registry (`incubacloud.mcp.catalog`) each module extends; a test fails on an unclassified `/cloud/*` route of any module built on it.
- **Approval.** Destructive and security-sensitive tools wait for the user: a form in the client, the panel's approval page (URL elicitation or `-32042`), or a link in the answer. `incubacloud.mcp.approval` binds the user, the credential, the tool and the arguments, ten minutes, once. It protects from the model's mistakes and from injected instructions, not from a malicious client.
- **Secrets.** Never in, never out: keys named like an encrypted field are refused and dropped, known values masked in every text.
- **Commands.** `run_command` and `run_host_command` are tool handlers with the terminals' controls, not routes: a route would open command execution to the SPA's cookie. One minute, kept by `timeout` inside the container; what a command leaves in the background is not stopped.
- **Audit.** `via_client` on audit rows and jobs names the verified credential and the declared client.

## Assistant (`incubacloud_assistant`)

A separate module: a chat in the panel, with the customer's own AI provider key, whose tools are the MCP's. Full reference in [`assistant.md`](assistant.md); user guide in `docs/user/docs/assistant/`.

- **A task is a chain of queue jobs** (channel `root.assistant`), one step each, run as the user: one call to the provider (`requests`, fixed addresses, no SDK) and the tools it asks for, each in a transaction of its own that writes nothing of the conversation.
- **Tools as the user.** `request_scope.tool_request` binds a request of the user's own inside the job, and `incubacloud.mcp.server._tools_call` runs the tool as it runs an agent's: role, schema, secret filter, savepoint, audit (*via agent* `Assistant (conversation N)`).
- **Confirmation cards.** `incubacloud.mcp.confirm._gate` answers the assistant's calls with a card in the chat (approval channel `assistant`) that only the person's own request answers; every change asks except trying code on a staging, and every change asks after the task read content others can write.
- **Conversations** are private to their owner (a global record rule, managers included), kept 30 days after their last activity, and usage is counted per user, month and model.

## Frontend SPA

The UI is an **OWL single-page application** served from `/cloud`. It uses a custom router with hash-free URLs.

### Routes

| Route | Path | Component |
|---|---|---|
| `projects` (home) | `/cloud`, `/cloud/projects` | Project dashboard |
| `new_project` | `/cloud/projects/new` | Project form |
| `project_detail` / `project_settings` | `/cloud/projects/:id[/settings]` | Project detail |
| `create_instance` | `/cloud/projects/:id/instances/new` | Instance form |
| `instance_detail` | `/cloud/projects/:id/instances/:iid` | Instance detail |
| `hosts` / `new_host` / `host_detail` | `/cloud/hosts[...]` | Hosts (manager-gated) |
| `settings` | `/cloud/settings?tab=…` | Settings (manager-gated) |
| `backup_backends` / detail / new | `/cloud/backup-backends[...]` | Backup backends |

Jobs and alerts are **slide-over panels** (not routes) opened from the header; notification preferences are a header modal. The router is extensible: private modules register additional routes with `registerRoute(name, parseFn, buildFn)`.

### Theme

Light and dark themes ship with the Relay design system (`scss/relay.scss`). The choice persists in `localStorage["ic-theme"]` and applies as `data-ic-theme` on `<html>` before mount (no flash). Default is light; the toggle lives in the user menu.

### Real-time updates

Two bus channels: `cloud_jobs` (job state changes; components re-fetch via `/cloud/get_job_brief`, project store refreshes debounced) and `cloud_overview` (alert badge refresh + per-user critical alert toasts). A visibility hook re-fetches on tab focus as a safety net.

### Pagination

Long lists use server-side `offset`/`limit` pagination (page size 20) with the `IcPager` component: alert history, instance backups, and audit logs. Dashboard-style lists are truncation-capped (limit 200 + banner) instead.

### Toast notifications

A global service injected through `useSubEnv` in the app shell:

```javascript
this.env.toast?.success("Instance deployed");   // auto-dismiss 4 s
this.env.toast?.error("Deploy failed: " + e);   // persistent until dismissed
this.env.toast?.warning("Unsaved changes");     // 6 s
this.env.toast?.info("Refreshing backups…");    // 4 s
```

The OWL `env` is frozen — never mutate it directly.

A button that enqueues says what became of its job, from the endpoint's answer or from `/cloud/get_job_state` (`utils/job_queue.js`, `announceJob`): "Started: <type>", "Queued behind <type>" or "Queued", never a "queued" that only meant "asked for". It opens no tab: the job's log opens from the job lists.

### Unsaved changes

Forms track dirtiness by comparing a JSON snapshot of the form state against the last saved snapshot. A shared nav-guard hook wires that into both the browser `beforeunload` event and the SPA's internal navigation (confirm dialog before route changes).

### Log pages

The job log terminal (`/cloud/log/<id>`) and the container log viewer (`/cloud/instance/<id>/logs`) are server-rendered pages opened in a new tab, not SPA routes. The job terminal streams over WebSocket with a 10 s polling fallback; the container viewer polls every 4 s.
